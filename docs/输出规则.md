# LLM Assembly 输出规则

## 1. 输出目标

`*.llm_assembly.json` 是面向后续 LLM 恢复 assembly 的输入文件。

它不是完整 S-SEIR，也不是最终 Solidity 源码恢复结果，而是从 S-SEIR 中抽取 assembly 相关的确定性语义事实，让 LLM 基于这些事实自行判断：

- 哪些 Yul / inline assembly 语义可以恢复为 Solidity-like 代码；
- 哪些语义无法无损恢复，需要保留 assembly 或给出说明。

## 2. 顶层结构

文件顶层结构为：

```json
{
  "schema": "s-seir-assembly-llm-input/v1",
  "description": "...",
  "functions": []
}
```

含义：

- `schema`：当前导出格式版本。
- `description`：说明该文件是 assembly-focused 的 S-SEIR 导出。
- `functions`：只包含存在 inline assembly / Yul 语句的函数。

不含 assembly 的普通 Solidity 函数不会进入该文件。

## 3. 函数级组织方式

`functions` 中每个元素对应一个函数级处理单元：

```json
{
  "function_id": "Token._transfer(address, address, uint256)",
  "contract": "Token",
  "function": "_transfer",
  "signature": "_transfer(address, address, uint256)",
  "llm_boundary": {},
  "source_statements": {},
  "control": {},
  "expression_roles": [],
  "effects": [],
  "semantic_overlays": []
}
```

组织原则：

- 以函数为单位，而不是以单个 `assembly {}` 块为单位。
- 同一函数中的 assembly 块会放在同一个函数对象中。
- Solidity 语句作为上下文保留，但重点仍是 assembly 部分。
- Yul 语句通过 `stmt_id` 与 CFG、effect、overlay 关联。

## 4. LLM 边界

`llm_boundary` 明确告诉后续消费端当前文件的职责边界：

```json
{
  "input_layers": [
    "source_statements",
    "control",
    "expression_roles",
    "effects",
    "semantic_overlays"
  ],
  "excluded_layers": [
    "security_facts",
    "analysis_facts",
    "projection_policies"
  ],
  "task": "..."
}
```

当前导出只保留前五层：

1. `source_statements`
2. `control`
3. `expression_roles`
4. `effects`
5. `semantic_overlays`

以下层不导出为 LLM 输入：

- `security_facts`
- `analysis_facts`
- `projection_policies`

原因是当前阶段希望 LLM 自行判断是否可恢复，而不是提前使用静态规则写死投影结论。

## 5. SourceStatements 层

`source_statements` 保存原始语句引用：

```json
{
  "solidity_context_statements": [],
  "assembly_statements": [],
  "assembly_blocks": []
}
```

含义：

- `solidity_context_statements`：函数中与 assembly 同属一个函数上下文的 Solidity 语句。
- `assembly_statements`：该函数内所有 Yul 语句的平铺列表。
- `assembly_blocks`：按 `asm_block_x` 分组后的 Yul 语句。

每条语句通常包含：

- `stmt_id`：语句唯一编号，例如 `asm_s_11`。
- `lang`：`solidity` 或 `yul`。
- `text`：原始语句文本。
- `src`：solc source range。
- `function_id`：所属函数。
- `block_id`：所属 assembly block。
- `origin`：原始 AST 节点类型等信息。

该层用于回答：

- 原始 Yul 写了什么；
- 每个语义节点来自哪条原始语句；
- 后续恢复时应替换或保留哪段 assembly。

## 6. Control 层

`control` 保存函数级 CFG：

```json
{
  "notes": [],
  "blocks": [],
  "edges": [],
  "loop_contexts": {}
}
```

组织规则：

- Solidity 函数级 CFG 来自 Slither。
- Yul / inline assembly 内部 CFG 来自本地 `assembly_ast_cfg`。
- Slither 中的 assembly anchor 节点会被本地 Yul CFG 子图替换。
- CFG 以函数为单位统一组织 Solidity block 和 Yul block。

`blocks` 中每个节点通常包含：

- `block_id`：CFG block 编号。
- `kind`：`solidity` 或 `yul`。
- `stmts`：该 block 对应的 `stmt_id`。
- `terminator`：控制流终止类型，如 `Branch`、`Return`、`Revert`、`Fallthrough`。
- `assembly_block`：若为 Yul block，则记录所属 assembly 块。
- `attrs`：Slither node id、Yul node id、源码范围、原始文本、loop 上下文等。

`edges` 表示控制流边：

- `from`：起始 block。
- `to`：目标 block。
- `kind`：边类型，如 `true`、`false`、`fallthrough`、`loop`。

该层用于让 LLM 理解：

- assembly 语句的执行顺序；
- if / revert / loop / fallthrough 关系；
- 某个 effect 是在哪条路径上发生的。

## 7. ExpressionRoles 层

`expression_roles` 记录表达式在语义恢复中的作用：

```json
{
  "expr_id": "expr_43",
  "text": "UbLX[_from]",
  "normalized": "UbLX[_from]",
  "role": "mapping_slot_expr",
  "type_hint": null,
  "stmt_ref": "asm_s_11",
  "attrs": {}
}
```

字段含义：

- `expr_id`：表达式角色编号。
- `text`：原始或恢复出的表达式文本。
- `normalized`：规范化后的表达式。
- `role`：表达式作用。
- `type_hint`：类型提示。
- `stmt_ref`：对应的原始语句。
- `attrs`：额外信息。

常见 `role` 包括：

- `branch_condition`
- `guard_condition`
- `memory_slice_start`
- `memory_slice_size`
- `memory_read_value`
- `storage_slot_expr`
- `storage_write_value`
- `mapping_slot_expr`
- `mapping_key_material`
- `state_access_expr`
- `event_topic0`
- `event_indexed_argument`
- `abi_argument`
- `call_target`
- `call_gas`
- `call_input_ptr`
- `call_input_size`
- `call_output_ptr`
- `call_output_size`

该层不是完整表达式 AST，而是告诉 LLM：

- 某个表达式在语义上扮演什么角色；
- 某个 `keccak256` 是否对应 mapping slot；
- 某个 log topic 是否是 event topic；
- 某个 call 参数是 target、gas、input 还是 output。

## 8. Effects 层

`effects` 保存底层副作用语义：

```json
{
  "effect_id": "eff_56",
  "kind": "StorageWrite",
  "stmt_refs": ["asm_s_23"],
  "attrs": {}
}
```

字段含义：

- `effect_id`：effect 编号。
- `kind`：副作用类型。
- `stmt_refs`：对应原始语句。
- `attrs`：该 effect 的详细参数。

常见 `kind` 包括：

- `MemoryWrite`
- `MemoryRead`
- `MemoryHash`
- `StorageRead`
- `StorageWrite`
- `Branch`
- `Revert`
- `Return`
- `EventLog`
- `Call`
- `StaticCall`
- `DelegateCall`
- `ValueDef`
- `BranchMaterialization`

该层只描述发生了什么底层行为，不直接判断是否可恢复为 Solidity。

例如：

- `mstore` 会记录为 `MemoryWrite`。
- `keccak256(ptr, size)` 会记录为 `MemoryHash`，并携带 memory read 结果。
- `sload(slot)` 会记录为 `StorageRead`。
- `sstore(slot, value)` 会记录为 `StorageWrite`。
- `log3(...)` 会记录为 `EventLog`。
- `staticcall(...)` 会记录为 `StaticCall`。

## 9. SemanticOverlays 层

`semantic_overlays` 是从底层 effect 恢复出的高级语义解释：

```json
{
  "overlay_id": "ov_17",
  "kind": "MappingWrite",
  "effects": ["eff_36", "eff_56"],
  "stmt_refs": ["asm_s_11", "asm_s_23"],
  "attrs": {
    "access": "UbLX[_from]",
    "value": "(qVPd - _amount)",
    "solidity_like": "UbLX[_from] = (qVPd - _amount);"
  }
}
```

字段含义：

- `overlay_id`：overlay 编号。
- `kind`：高级语义类型。
- `effects`：该 overlay 由哪些底层 effect 组成。
- `stmt_refs`：对应的原始语句。
- `attrs`：高级语义信息。

常见 `kind` 包括：

- `RequireOverlay`
- `MappingSlot`
- `MappingRead`
- `MappingWrite`
- `PathConditionedStorageRead`
- `PathConditionedStorageWrite`
- `StateVariableRead`
- `StateVariableWrite`
- `EventEmit`
- `PrecompileCall`
- `PrecompileOutputRead`
- `ExpressionNormalization`

该层是 LLM 恢复源码时最重要的输入之一。

例如：

- `RequireOverlay` 说明某段 `if { revert(0,0) }` 可理解为 require-like 语义。
- `MappingRead` 说明某个 `sload(keccak256(...))` 实际读取 mapping。
- `MappingWrite` 说明某个 `sstore(...)` 实际写入 mapping。
- `EventEmit` 说明某个 `logN` 对应 Solidity event。
- `PrecompileCall` 说明某个低级 call 目标是 Ethereum precompile。

## 10. 过滤规则

该文件只导出 assembly 相关内容。

函数过滤：

- 只导出包含 Yul / inline assembly 语句的函数。
- 不含 assembly 的普通函数不会进入 `functions`。

ExpressionRole 过滤：

- 只保留 `stmt_ref` 指向 Yul 语句的表达式角色。

Effect 过滤：

- 保留 `stmt_refs` 中包含 Yul 语句的 effect。
- `BranchMaterialization` 作为 assembly 分支处理结果也会保留。

Overlay 过滤：

- 保留直接引用 Yul 语句的 overlay。
- 如果 overlay 依赖的 effect 来自 assembly，也会保留。

不导出的内容：

- 安全分析事实；
- 内部调试用 analysis facts；
- 静态投影判断；
- 不含 assembly 的纯 Solidity 函数语义。

## 11. LLM 使用方式

建议 LLM 按以下顺序消费该文件：

1. 先阅读 `source_statements.assembly_blocks`，理解原始 Yul。
2. 再阅读 `control`，理解执行路径和分支结构。
3. 用 `expression_roles` 理解关键表达式的语义角色。
4. 用 `effects` 确认底层 memory / storage / call / log / revert 行为。
5. 用 `semantic_overlays` 生成 Solidity-like 恢复草案。
6. 最后由 LLM 自行判断哪些 overlay 可以组合成 Solidity 代码，哪些必须保留 assembly。

当前导出不要求 LLM 重新推断底层 slot、event、memory 来源；这些已经由 S-SEIR 的确定性分析完成。

LLM 的主要任务是：

- 组织语句顺序；
- 合并重复的 SSA / path-conditioned 结果；
- 将 `solidity_like` 片段组合为可读源码；
- 对无法无损恢复的低层语义保留 assembly 或添加说明。

## 12. 与完整 S-SEIR 的区别

完整 S-SEIR 输出包含更多内容，例如：

- `security_facts`
- `analysis_facts`
- CFG 调试信息
- MemorySSA 查询细节
- 内部归档信息

`*.llm_assembly.json` 则是压缩后的 LLM 输入视图：

- 保留语义恢复所需的前五层；
- 删除与源码恢复无直接关系的分析层；
- 不提前做 ProjectionPolicy 判断；
- 将是否可恢复交给后续 LLM。

因此，该文件可以视为：

```text
完整 S-SEIR -> assembly-focused deterministic semantic facts -> LLM assembly recovery input
```

## 13. Compact 输出规则

在保留原 `*.llm_assembly.json` 完整五层导出的基础上，当前新增 compact 输出：

```text
*.llm_assembly.compact.json
*.llm_assembly.compact.txt
```

compact 输出不会替代原输出。原输出仍用于调试和程序消费；compact 输出用于一次 LLM 问询中的 assembly 恢复。

### 13.1 顶层结构

compact 顶层结构为：

```json
{
  "schema": "s-seir-assembly-llm-compact/v1",
  "functions": []
}
```

与完整 LLM assembly 输出相比：

- 去除了顶层 `description`；
- 只保留 `schema` 和 `functions`；
- 避免把说明性文本反复喂给 LLM。

### 13.2 函数级结构

每个函数对象结构为：

```json
{
  "function_id": "...",
  "contract": "...",
  "function": "...",
  "signature": "...",
  "recovery_task": "...",
  "function_source": {},
  "assembly_blocks": [],
  "control_summary": {},
  "key_expression_roles": [],
  "effect_summary": {},
  "semantic_overlays": [],
  "unresolved_low_level_semantics": []
}
```

核心变化：

- 保留 assembly 所在完整函数源码。
- 保留 assembly 块原始源码片段。
- 不再导出完整 `source_statements`、完整 CFG、完整 effect attrs。
- 以 `semantic_overlays` 为主体。

### 13.3 Function Source

`function_source` 保存 assembly 所在完整函数：

```json
{
  "src": "2079:1372:0",
  "text": "function _transfer(...) { ... }"
}
```

目的：

- 保留函数参数、返回值、visibility、modifier。
- 保留 assembly 前后的 Solidity 语句。
- 保留局部变量和作用域上下文。
- 让 LLM 不需要只依赖抽象语义猜测函数结构。

### 13.4 Assembly Blocks

`assembly_blocks` 保存源码中的 assembly 原文：

```json
[
  {
    "block_id": "asm_block_1",
    "src": "...",
    "text": "assembly { ... }"
  }
]
```

目的：

- 作为语义恢复的源码锚点。
- 允许 LLM 对照原始 Yul。
- 避免导出所有 `asm_s_x` 原始语句造成 token 膨胀。

### 13.5 Control Summary

`control_summary` 是完整 CFG 的摘要：

```json
{
  "block_count": 40,
  "edge_count": 46,
  "assembly_cfg_block_count": 39,
  "has_branch": true,
  "has_loop": true,
  "notes": [],
  "assembly_blocks": [1]
}
```

compact 不导出完整 CFG blocks / edges。

原因：

- 完整 CFG 对调试有用，但对 LLM 恢复源码通常过长。
- LLM 更需要知道是否存在分支、循环、assembly 子图，而不是每条 CFG 边的完整细节。

如需调试路径，可继续使用完整 `*.llm_assembly.json` 或 CFG dot/png。

### 13.6 Key Expression Roles

`key_expression_roles` 只保留关键表达式角色，例如：

- `guard_condition`
- `branch_condition`
- `mapping_slot_expr`
- `mapping_key_material`
- `state_access_expr`
- `storage_slot_expr`
- `storage_write_value`
- `event_topic0`
- `event_indexed_argument`
- `abi_argument`
- `call_target`
- `call_gas`
- `call_input_ptr`
- `call_input_size`
- `call_output_ptr`
- `call_output_size`

不再导出所有 expression roles。

### 13.7 Effect Summary

`effect_summary` 只保存 effect 统计和少量关键 effect：

```json
{
  "counts": {
    "MemoryWrite": 22,
    "StorageRead": 3,
    "StorageWrite": 2
  },
  "selected_effects": []
}
```

完整 MemorySSA、memory read result、branch candidates、resolved inputs 等大型结构不会完整进入 compact 输出。

这些底层事实已经被 S-SEIR 用于生成 overlay；LLM 默认消费 overlay 即可。

### 13.8 Semantic Overlays

`semantic_overlays` 是 compact 输出主体。

每个 overlay 保留：

- `overlay_id`
- `kind`
- `effects`
- `stmt_refs`
- 精简后的 `attrs`

例如：

```json
{
  "overlay_id": "ov_17",
  "kind": "MappingWrite",
  "effects": ["eff_36", "eff_56"],
  "stmt_refs": ["asm_s_11", "asm_s_23"],
  "attrs": {
    "access": "UbLX[_from]",
    "value": "(qVPd - _amount)",
    "solidity_like": "UbLX[_from] = (qVPd - _amount);"
  }
}
```

不同 overlay 按类型保留不同核心字段：

- `RequireOverlay`：保留 require-like 条件。
- `MappingRead / MappingWrite`：保留 mapping 访问表达式和 Solidity-like 语句。
- `StateVariableRead / StateVariableWrite`：保留状态变量访问。
- `EventEmit`：保留 event 名称、topic、参数。
- `PrecompileCall`：保留 precompile 目标和 Solidity-like 调用。
- `ExpressionNormalization`：保留基础表达式规范化结果。
- `PathConditionedStorageRead / Write`：保留路径条件摘要和候选恢复结果。

### 13.9 Unresolved Low-level Semantics

`unresolved_low_level_semantics` 记录仍需要 LLM 特别注意的低层语义：

```json
[
  {
    "effect_id": "...",
    "kind": "StaticCall",
    "stmt_refs": [],
    "summary": {}
  }
]
```

用途：

- 提醒 LLM 某些 call / revert / return / create 等低层语义可能不能无损恢复。
- 这部分不是静态投影结论，只是恢复时需要关注的语义残留。

### 13.10 使用建议

默认给 LLM 使用 compact 输出。

推荐顺序：

1. 读取 `function_source`，理解完整函数上下文。
2. 读取 `assembly_blocks`，定位待恢复的 assembly。
3. 查看 `control_summary`，判断是否有复杂分支或循环。
4. 以 `semantic_overlays` 作为主要恢复依据。
5. 参考 `effect_summary` 和 `key_expression_roles` 补充判断。
6. 对 `unresolved_low_level_semantics` 中的内容谨慎处理，必要时保留 assembly。

完整 `*.llm_assembly.json` 仍保留，用于：

- 调试 S-SEIR；
- 查看完整五层结构；
- 追踪具体 effect 的 MemorySSA / CFG / path 细节；
- 排查 overlay 恢复错误。
