## 1. 函数级输出结构

当前 S-SEIR 以函数为单位输出。`FunctionSSEIR.to_dict()` 中真实存在的字段是：

```text
function_id
contract
function
signature
source_statements
control
expr_roles
effects
semantic_overlays
security_facts
analysis_facts
```

批处理输出会在这个函数级核心结构外附加：

```text
function_source
assembly_sources
```

这两个字段用于人工审计和 solidity-like 导出，不是 `FunctionSSEIR` dataclass 本身的语义层。

目前代码中没有单独输出 `projection_policies` 层。可否恢复为 Solidity 的判断主要体现在 `semantic_overlays[*].attrs.solidity_like`、`reason`、`unresolved_reason`，以及 `solidity-like` 导出视图中。

## 2. Source Statements

`source_statements` 保存原始 Solidity / Yul 语句。后续所有 effect、overlay、fact 都通过 `stmt_refs` 回指原语句。

典型字段：

```text
stmt_id
lang
text
src
function_id
block_id
origin
```

判断规则：

```text
SourceStatementCollector 从 solc AST 中提取函数内 Solidity 语句与 inline assembly/Yul 语句，并给每条语句分配 stmt_id。
```

## 3. Control 层

`control` 是函数级 CFG。当前实现采用混合方式：

```text
Solidity 函数 CFG：优先使用 Slither function.nodes
Yul CFG：使用本项目原 assembly_ast_cfg.build_yul_cfg
拼接策略：将 Slither 中 assembly 范围内的节点替换为本地 Yul CFG 子图
```

实际记录：

```text
blocks
edges
notes
loop_contexts
```

其中 block 分为：

```text
kind = solidity
kind = yul
```

terminator 支持：

```text
Branch
Return
Revert
Stop
Terminal
Fallthrough
YulNode
```

循环上下文：

```text
ControlBuilder 会从 solc AST 中识别 Solidity 的 ForStatement / WhileStatement / DoWhileStatement。
如果 assembly 块位于这些 loop 范围内，则在 control.loop_contexts 中给该 assembly_block 附加 function-level loop context。
```

如果 Slither 不可用，则退化为 Solidity 顺序骨架 + Yul CFG 子图。

### 3.1 CFG 构建前的分支预处理

正式 CFG、MemorySSA 和 Source Statement Table 均基于分支预处理后的 `analysis_source` 构建。预处理包含两个独立步骤。

第一步是保守 opaque-if 剪枝，只处理 AST 定位的 Yul `if`，并且只接受可由语法恒等式证明的条件：

```text
eq(x, x)                         -> true
sub(x, x) / xor(x, x)            -> 0
mul(x, 0) / and(x, 0)            -> 0
add(x, 0) / or(x, 0) / xor(x, 0) -> x（用于等价比较）
and(x, x)                        -> x（用于等价比较）
mul(a, b) 与 mul(b, a)           -> 等价
iszero(已证明条件)               -> 取反
```

示例：

```yul
if eq(x, x) {
    mstore(ptr, value)
}
```

条件被证明恒真后，预处理源码只保留 body：

```yul
mstore(ptr, value)
```

符号条件、范围推理、业务条件和仅“看起来可疑”的表达式不会被剪枝。

第二步是 memory sink 分支物化。它复用原 `BranchExpansion + MemorySSA PathSlice` 算法，处理：

```text
log0-log4
call / callcode / staticcall / delegatecall
return / revert
```

当同一 sink 的 memory 输入在不同路径上具有不同的已知 SSA slice 时，预处理把 sink 及其必要数据来源写入对应 condition：

```yul
mstore(0, a)
if cond { mstore(0, b) }
log1(0, 0x20, topic)
```

物化后的分析源码表达为：

```yul
if iszero(cond) {
    mstore(0, a)
    log1(0, 0x20, topic)
}
if cond {
    mstore(0, b)
    log1(0, 0x20, topic)
}
```

处理规则：

```text
1. 从 sink 所在 CFG node 的全部 PathState 解析 pointer/length 对应的 memory range。
2. 按 resolved signature 合并相同来源，只物化真正分歧的 memory/value SSA node。
3. 所有路径共有的定义不重复搬入子分支。
4. unknown path 不用于猜测；有已知路径时可丢弃 unknown path 并在报告中记录。
5. 去除 unknown 后只剩一个已知 signature 时，将其线性化，不保留无意义 condition。
6. 不重写嵌在 Yul condition 内部的 call-family sink，避免破坏整个 YulIf body。
```

有 imports 时，每个可解析 source unit 先独立执行上述预处理，再递归 flatten 为单一 `analysis_source`；重复 import 只保留一次。所有来源文件和 rewrite 数量写入 `SSEIRBranchPreprocess`。

### 3.2 Solidity 条件向 assembly effect 的前缀传播

Function-level CFG 中，若 assembly 入口 `bb_asmN_n0` 的直接前驱是 Solidity `Branch`，EffectLifter 会提取该入口条件：

```text
true / if_true edge  -> condition
false edge           -> !(condition)
```

随后把该前缀与 assembly 内部 MemorySSA path predicates 合并：

```text
Solidity prefix = ownerChecksEnabled
Yul local path  = iszero(check)

effect.path_states = [ownerChecksEnabled && iszero(check)]
```

示例：

```solidity
if (_guardInitializeOwner()) {
    assembly {
        sstore(_OWNER_SLOT, newOwner)
    }
}
```

`StorageWrite.path_states` 至少记录：

```json
["_guardInitializeOwner()"]
```

该条件随后传递给 path-conditioned storage candidate、event/revert overlay 和 solidity-like 展示。
当前实现读取 assembly 入口的直接 CFG branch 前缀；更深层的 Solidity 条件是否完整出现，取决于 Slither 融合 CFG 是否已经把它们保留到该入口边。

### 4.1 MemoryByteAxis

目的：

```text
补强 word-level MemorySSA 无法准确处理的非 32 字节对齐、重叠写入场景。
典型场景是 hash scratch space / ABI scratch space 中的 packed memory 构造。
```

实现位置：

```text
scripts/s_seir/s_seir_memory_ssa.py
```

基本规则：

```text
1. 只处理静态可定位地址和长度，例如 0x00 / 0x0c / 0x20。
2. mstore(addr, value) 按 32 字节写入 MemoryByteAxis：
   memory[addr + 0]  = value[0]
   ...
   memory[addr + 31] = value[31]
3. mstore8(addr, value) 按 1 字节写入：
   memory[addr] = value[31]
4. 按 node_id 顺序重放写入，后写入自然覆盖前写入。
5. 语义终点执行 memory query 时，查询结果附加 byte_slice。
```

`byte_slice` 记录：

```text
query_kind = MemoryByteSliceResult
tracker_scope = s_seir_memory_byte_axis
pointer / length / start / size
complete
has_overlap
slices
path_slices
packed_semantics
```

每个 slice 记录：

```text
query_offset
size
source_value
source_range
source_version
source_node_id
source_kind
extraction
overlap_count
```

示例：

```yul
mstore(0x0c, _HANDOVER_SLOT_SEED)
mstore(0x00, caller())
sstore(keccak256(0x0c, 0x20), expires)
```

对 `keccak256(0x0c, 0x20)` 的 byte-axis 解析结果：

```text
[0, 20)  <- caller()[12, 32]              -> bytes20(msg.sender)
[20, 32) <- _HANDOVER_SLOT_SEED[20, 32]   -> low_bytes(_HANDOVER_SLOT_SEED, 12)
```

最终 packed input：

```text
keccak256(abi.encodePacked(bytes20(msg.sender), low_bytes(_HANDOVER_SLOT_SEED, 12)))
```

当前测试样例：

```text
1. overlapping handover slot:
   mstore(0x0c, _HANDOVER_SLOT_SEED)
   mstore(0x00, caller())
   read 0x0c..0x2c
   -> [bytes20(msg.sender), low_bytes(_HANDOVER_SLOT_SEED, 12)]

2. revert selector partial slice:
   mstore(0x00, 0x82b42900)
   read 0x1c..0x20
   -> [low_bytes(0x82b42900, 4)]

3. mstore8 overwrite:
   mstore(0x00, wordValue)
   mstore8(0x1f, byteValue)
   read 0x00..0x20
   -> [high_bytes(wordValue, 31), low_bytes(byteValue, 1)]
```

### 4.2 SinkResolver

实现位置：

```text
scripts/s_seir/s_seir_sink_resolver.py
```

`SinkResolver` 是当前 S-SEIR 中的统一语义终点解析层。

它不重新构建 MemorySSA，也不重新枚举 CFG 路径；它消费 effect 中已经存在的 memory query / byte-axis 结果，并把不同 effect 的 memory 参数统一整理为 `effect.attrs.sink_resolution`。

当前接入点：

```text
s_seir_overlay_builder.py

OverlayBuilder.build()
  -> SinkResolver().attach_all(effects)
  -> overlay builder 读取 effect.attrs.sink_resolution
```

支持的语义终点：

```text
MemoryHash
EventLog
Return
Revert
Call
StaticCall
DelegateCall
CallCode
```

每类 sink 的 memory role：

```text
MemoryHash   -> role=slot      memory_attr=memory_read     semantic_role=hash_input
EventLog     -> role=data      memory_attr=data_memory     semantic_role=event_data
Return       -> role=payload   memory_attr=payload_memory  semantic_role=return_payload
Revert       -> role=payload   memory_attr=payload_memory  semantic_role=revert_payload
Call         -> role=input     memory_attr=input_memory    semantic_role=call_input
StaticCall   -> role=input     memory_attr=input_memory    semantic_role=staticcall_input
DelegateCall -> role=input     memory_attr=input_memory    semantic_role=delegatecall_input
CallCode     -> role=input     memory_attr=input_memory    semantic_role=callcode_input
```

`sink_resolution` 实际结构：

```json
{
  "sink_id": "sink_asm_s_4_Return_12",
  "stmt_refs": ["asm_s_4"],
  "cfg_node_id": 12,
  "sink_kind": "Return",
  "args": ["0", "0x20"],
  "path_sensitive": true,
  "path_resolutions": [
    {
      "path_id": "path_0",
      "condition": "!(cond)",
      "status": "resolved",
      "reason": null,
      "arg_resolutions": {
        "payload": {
          "expr": "0:0x20",
          "normalized": "MemorySlice(a)",
          "ssa_key": null,
          "memory_slice": {
            "query_kind": "PathMemoryByteSlice",
            "path": "!(cond)",
            "complete": true,
            "slices": [
              {
                "query_offset": 0,
                "size": 32,
                "extraction": "a",
                "source_version": "a__ssa1",
                "source_node_id": 2
              }
            ]
          },
          "notes": [
            "return_payload",
            "byte_axis_memory_slice",
            "path_sensitive_sink"
          ]
        }
      }
    }
  ]
}
```

核心判断规则：

```text
1. 只处理已有 byte_slice 且 complete=true 的 memory query。
2. 如果 byte_slice.path_slices 存在，则逐 path 生成 SinkPathResolution。
3. 如果没有 path_slices，但有普通 slices，则视为 entry path。
4. 每条 path 保留 condition、slices、extraction、source_version、source_node_id。
5. 如果某条 path 的 slices 不完整或缺少 extraction，则该 path 标记 unresolved。
6. 如果不同 path 的 slice_signature 不同，或 path 带 condition，则 path_sensitive=true。
7. Hash sink 的 normalized 为 keccak256(abi.encodePacked(...))。
8. 普通 memory range sink 的 normalized 为 MemorySlice(...)。
```

`slice_signature` 会同时包含：

```text
query_offset
size
extraction
source_version
source_node_id
```

因此同名变量的不同 SSA 版本不会被压扁为同一个来源。

### 4.3 线性地址 alias 与 known-value 记录

实现位置：

```text
scripts/s_seir/s_seir_memory_ssa.py
```

目的：

```text
同一 memory 地址可能由 ptr、input、add(ptr, 12) 等多个表达式表示。
MemorySSA 在查询时需要把这些表达式归到同一基址和偏移，
并标明恢复出来的值是否具有可继续追踪的符号来源。
```

线性 alias 规则：

```text
1. 整数字面量可作为静态基址。
2. 标识符 x 记录为 base=x, offset=0。
3. add(base, constant) 记录为 base + constant。
4. sub(base, constant) 记录为 base - constant。
5. add(constant, base) 与 add(base, constant) 等价。
6. 如果标识符的 ValueDef 仍是线性 add/sub 或另一标识符，递归保留所有线性 alias。
7. 非线性表达式只保留为 symbolic/original alias，不推断等价关系。
```

示例：

```yul
let base1 := add(base0, 4)
let addr := add(base1, 4)
mstore(addr, value)
```

该 `MemoryWrite.aliases` 可同时包含：

```json
[
  {
    "base": "base0",
    "offset": 8,
    "expression": "base0 + 8"
  },
  {
    "base": "base1",
    "offset": 4,
    "expression": "base1 + 4"
  },
  {
    "base": "addr",
    "offset": 0,
    "expression": "addr"
  }
]
```

`known_value` 的实际记录类型：

```text
constant       整数常量
evm_builtin    msg.sender / caller() / timestamp() / gas() 等 EVM 环境值
symbolic_known 任意简单标识符或 x.slot 形式
derived_known  其他未显式标记 unknown 的复合表达式
unknown        缺少可用来源
```

注意：

```text
known=true 表示“该字节有可记录的符号来源”，
不表示静态分析已经求出了具体数值。
当前 `known_value_info` 是表达式可追踪性标记，不负责证明简单标识符一定属于函数参数、返回值或状态变量；
该归属由 TypeEnv、Source Statement 和后续 overlay 模式共同约束。
```

### 4.4 Function-level 多 assembly MemorySSA 桥接

当同一 Solidity 函数中有多个 assembly 块时，当前实现仍对每个 Yul 块单独调用底层 MemorySSA，但会在 S-SEIR 查询层建立函数级内存桥接。

实现步骤：

```text
1. 保存前一 assembly 块的 exit PathState 快照，最多保留 8 个。
2. 检查两个 assembly 块之间的 Solidity 源码。
3. 如果中间区域只包含值计算，将前块 exit memory 克隆到后块查询状态。
4. 如果出现 new/abi.* /低层调用/普通函数调用/return/revert 等可能改变 memory 的语句，中断桥接。
5. 当前 assembly 块的写入覆盖继承快照中的同地址定义。
6. 只继承函数级可持久的 value name：参数、返回值、Solidity 局部变量和状态变量。
```

桥接记录在 memory query 的：

```json
{
  "function_memory_bridge": [
    {
      "kind": "FunctionLevelAssemblyMemoryBridge",
      "from_assembly_block": 1,
      "to_assembly_block": 2,
      "policy": "inherit_exit_memory_snapshot",
      "safe": true,
      "reason": "value_only_solidity_span"
    }
  ]
}
```

继承的 memory version 使用新名称：

```text
bridge_b2_mem_1
```

并保留：

```text
inherited_from_version = mem_1
```

示例：

```solidity
assembly { mstore(0x00, x) }
uint256 y = x + 1;
assembly { let h := keccak256(0x00, 0x20) }
```

第二个 assembly 块查询 `0x00..0x20` 时可追踪到第一个 assembly 块的 `x`。如果中间改为 `bytes memory b = abi.encode(x)`，则记录：

```text
policy = break_on_possible_solidity_memory_mutation
safe = false
reason = abi_memory_operation
```

### 4.5 MemorySSA 与 SinkResolver 的查询优先级

当前规则是补充关系，不是 SinkResolver 覆盖 MemorySSA：

```text
1. 先读取普通 MemorySSA / loop lazy materialization 结果。
2. 如果静态长度可解析，再尝试 MemoryByteAxis。
3. byte-axis 完整时，它可以用更精确的字节切片替换 word 级查询结果。
4. SinkResolver 把已存在的 query 整理成逐路径 sink_resolution。
5. 如果 MemorySSA 本身完整，SemanticSinkMemoryQuery.resolved_by = memory_ssa。
6. 如果是逐路径 sink 恢复，resolved_by = sink_resolver。
7. 如果原始 memory range 不完整，但严格的高级模式已匹配，resolved_by = semantic_overlay_pattern。
8. 三者都不能完成恢复时，保留 unresolved，不伪造输入值。
```

示例：`DN404._packedLogsSend` 的 call input size 是符号表达式 `n`，普通 `input_memory` 可以是不完整的；但从 selector 写入、ABI head、`p.logs` 类型和 input-size 模式可以严格匹配：

```text
AbiCallDataConstruction.complete = true
SemanticSinkMemoryQuery.resolved_by = semantic_overlay_pattern
```

底层 `LowLevelCall.input_memory` 仍保留不完整记录，不会被高级 overlay 删除。

Solidity-like 示例：



### 5.3.2 MemoryArrayConstruction

来源：

```text

```

这不是按源码文本逐行匹配，而是按底层 effect 模式匹配：

```text

  result := mload(0x40)

ValueDef:
  cursor := add(result, 0x20)

  memory[cursor] = element
  或 memory[result + 32 + offset] = element

  memory[result] = length
```



### 6.2 RawRevertBytes

来源：

```text
revert(add(32, bytesObj), mload(bytesObj))
```

判断规则：

```text
payload_ptr 被 ExpressionRole 标注为 revert_payload_ptr。
对象必须被 TypeEnv 判断为 bytes memory。
payload_size 等于 bytesObj.length，或来自 mload(bytesObj)。
```

记录：

```text
source_object
payload = bytesObj[0:bytesObj.length]
guard
```

实际例子：

```solidity
function _revert(bytes memory returndata) private pure {
    if (returndata.length > 0) {
        assembly {
            let returndata_size := mload(returndata)
            revert(add(32, returndata), returndata_size)
        }
    }
}
```

底层 effect 形态：

```json
[
  {
    "kind": "MemoryRead",
    "attrs": {
      "read_from": "returndata",
      "value": "returndata_size"
    }
  },
  {
    "kind": "Revert",
    "attrs": {
      "payload_ptr": "add(32, returndata)",
      "payload_size": "returndata_size"
    }
  }
]
```

Expression Role 先把指针识别为 bytes 数据区：

```json
{
  "role": "revert_payload_ptr",
  "text": "add(32, returndata)",
  "normalized": "returndata.data",
  "attrs": {
    "object": "returndata"
  }
}
```

随后 `raw_revert_bytes()` 检查：

```text
1. 当前 effect 必须是 Revert；
2. Revert 的 stmt_refs 上存在 role=revert_payload_ptr；
3. role.attrs.object 是 bytes memory；
4. payload_size 等于 object.length，或 payload_size 来自 mload(object) 的 MemoryRead value。
```

生成的高级 overlay：

```json
{
  "kind": "RawRevertBytes",
  "attrs": {
    "source_object": "returndata",
    "payload": "returndata[0:returndata.length]",
    "guard": "returndata.length > 0"
  }
}
```

语义说明：

```text
这表示“原样转发 bytes memory 中保存的 revert payload”。
它不是 revert(string(returndata))，因为后者会重新 ABI 编码 Error(string)，语义不同。
因此 solidity-like 视图不会把它强行改写成普通 Solidity revert(string)。
```

```text
custom_error_selector_overlays()
  -> selector_info_from_payload(Revert, preferred_kind="error")
  -> 优先从 payload_memory.byte_slice.packed_semantics 解析 selector
  -> 如果 byte_slice 不可用，再回退到 payload_memory_partial
  -> selector_registry 匹配 error selector
```

生成形态：

```json
{
  "kind": "CustomErrorRevert",
  "attrs": {
    "selector": "0xd125259c",
    "selector_source": "low_bytes(0xd125259c, 4)",
    "error": "LinkMirrorContractFailed()",
    "revert_like": "revert LinkMirrorContractFailed();",
    "selector_match": {
      "match_status": "matched",
      "preferred_kind": "error"
    }
  }
}
```

如果 selector 没有匹配到源码中的 error 定义，则不会生成这个 selector 型 `CustomErrorRevert`，底层 `Revert` 仍保留在 effects 中。

重叠 memory 示例：

```yul
mstore(0x0c, _HANDOVER_SLOT_SEED)
mstore(0x00, pendingOwner)
if gt(timestamp(), sload(handoverSlot)) {
    mstore(0x00, 0x6f5e8818) // NoHandoverRequest()
    revert(0x1c, 0x04)
}
```

`payload_memory_partial` 可能同时看到 `_HANDOVER_SLOT_SEED` 和 `0x6f5e8818` 对 `0x1c..0x20` 的覆盖候选。此时以 `payload_memory.byte_slice` 为准：

```text
payload_memory.byte_slice.packed_semantics
  = [low_bytes(0x6f5e8818, 4)]
```

恢复结果：

```json
{
  "kind": "CustomErrorRevert",
  "attrs": {
    "selector": "0x6f5e8818",
    "error": "NoHandoverRequest()",
    "revert_like": "revert NoHandoverRequest();"
  }
}
```

### 6.4 MappingSlot / MappingRead / MappingWrite

来源：

```text
keccak256(memory[key, slot], 64)
sload(hash)
sstore(hash, value)
```

判断规则：

```text
MemoryHash 先作为候选保存。
只有 sload/sstore 消费该 hash 的 SSA slot version 时才激活 MappingSlot。
MemoryHash 的输入 words 必须能恢复为 key + base slot。
base slot 可以来自 state variable slot，也可以来自 storage reference 参数或局部 storage reference 的 .slot。
state variable slot 来自 TypeEnv / storage layout。
storage reference slot 来自 TypeEnv 中的参数/局部变量类型和 struct 字段布局。
```

支持 nested mapping：

```text
如果 base 本身是已激活 mapping slot，则生成 nested_mapping_slot。
```

支持 storage reference mapping：

```text
如果 base = X.slot，且 X 是 storage reference：
  - 若 X 本身是 mapping storage 参数，则恢复为 X[key]
  - 若 X 是 struct storage 参数，且 struct 在对应 slot offset 上有 mapping 字段 f，则恢复为 X.f[key]

如果 base = add(X.slot, n)，则用 n 作为 struct storage field slot offset。
```

这一步仍然由 storage sink 触发：

```text
1. keccak256(...) 先只作为 MemoryHash 候选保存；
2. sload/sstore 的 slot 参数消费该 hash 的 SSA version；
3. 才激活 MappingSlot，并倒推 hash 的 memory words；
4. 如果 word1 是 storage reference root，则结合 TypeEnv 恢复 X.f[key]。
```

多版本 slot：

```text
如果同一 storage effect 有多个 slot_versions，则生成 PathConditionedStorageRead / PathConditionedStorageWrite。
每个 candidate 单独记录 resolved/unresolved、access、solidity_like。
```

示例：storage reference 参数中的 struct mapping。

源码：

```solidity
struct Uint32Map {
    mapping(uint256 => uint256) map;
}

function _set(Uint32Map storage map, uint256 index, uint32 value) private {
    assembly {
        mstore(0x20, map.slot)
        mstore(0x00, shr(3, index))
        let s := keccak256(0x00, 0x40)
        let v := sload(s)
        sstore(s, value)
    }
}
```

MemoryHash 的 resolved inputs：

```text
word0 = shr(3, index)
word1 = map.slot
```

TypeEnv 识别：

```text
map:
  type = struct DN404.Uint32Map
  data_location = storage

Uint32Map fields:
  slot_offset 0 -> map: mapping(uint256 => uint256)
```

因此 slot 恢复为：

```text
keccak256(shr(3, index), map.slot)
-> map.map[index >> 3]
```

Overlay 记录：

```json
{
  "kind": "MappingSlot",
  "attrs": {
    "expression": "map.map[(index >> 3)]",
    "storage_reference": "map",
    "storage_reference_type": "struct DN404.Uint32Map",
    "storage_reference_kind": "struct_mapping_storage_ref",
    "storage_field": {
      "name": "map",
      "type_string": "mapping(uint256 => uint256)",
      "index": 0
    },
    "key": "(index >> 3)",
    "base": "map.slot",
    "slot_kind": "storage_ref_mapping_slot",
    "activation": "storage_consumer",
    "notes": ["storage_reference_mapping_slot"]
  }
}
```

对应读写恢复：

```text
v = map.map[(index >> 3)];
map.map[(index >> 3)] = value;
```

### 6.5 StateVariableRead / StateVariableWrite

来源：

```text
sload(slot)
sstore(slot, value)
Branch condition / EvaluationStep 中的 sload(slot)
```

判断规则：

```text
如果 slot 可以通过 TypeEnv.state_var_by_slot 映射到状态变量，则恢复为状态变量读写。
如果 slot 是源码中定义的 constant，或 slot 变量可通过 ValueDef 追溯到 constant，则恢复为 constant storage slot。
如果 slot 来自先前 MemoryHash，并且 MemoryHash 可通过 MemoryByteAxis 恢复为手工 packed hash slot，则恢复为 manual_packed_hash_slot。
否则保留为 storage[slot]，并记录 unresolved_reason=unknown_storage_slot。
```

condition 内嵌 `sload`：

Yul 的条件表达式中经常直接嵌入 `sload`：

```yul
if gt(timestamp(), sload(handoverSlot)) {
    revert(0x1c, 0x04)
}
```

S-SEIR 的 CFG 层已经把该语句建模为 `Branch`，并通过 Yul evaluation order 拆出求值步骤：

```text
__tmp_1 = sload(handoverSlot)
__tmp_2 = timestamp()
__tmp_3 = gt(__tmp_2, __tmp_1)
Branch(__tmp_3)
```

现在 EffectLifter 会把 EvaluationStep 中的 `sload(handoverSlot)` 同步提升为 `StorageRead`：

```json
{
  "kind": "StorageRead",
  "attrs": {
    "slot": "handoverSlot",
    "slot_versions": ["handoverSlot__ssa1"],
    "value": "__tmp_1",
    "nested_in_condition": true
  }
}
```

随后 `storage_overlays()` 复用普通 storage consumer 逻辑，把它归档成 `StateVariableRead`：

```json
{
  "kind": "StateVariableRead",
  "attrs": {
    "target": "__tmp_1",
    "access": "storage[keccak256(abi.encodePacked(low_bytes(pendingOwner, 20), low_bytes(_HANDOVER_SLOT_SEED, 12)))]",
    "storage_model": "manual_packed_hash_slot",
    "state_access": true,
    "state_mutation": false,
    "slot_derivation": {
      "kind": "manual_packed_hash_slot",
      "hash": "keccak256",
      "encoding": "abi.encodePacked",
      "packed_inputs": [
        "low_bytes(pendingOwner, 20)",
        "low_bytes(_HANDOVER_SLOT_SEED, 12)"
      ]
    }
  }
}
```

solidity-like 中该求值步骤展示为：

```solidity
__tmp_1 = storage[keccak256(abi.encodePacked(low_bytes(pendingOwner, 20), low_bytes(_HANDOVER_SLOT_SEED, 12)))];
```

constant storage slot 示例：

```solidity
bytes32 internal constant _OWNER_SLOT =
    0xffffffffffffffffffffffffffffffffffffffffffffffffffffffff74873927;
```

Yul：

```yul
let ownerSlot := _OWNER_SLOT
sstore(ownerSlot, newOwner)
```

S-SEIR 记录：

```json
{
  "kind": "StateVariableWrite",
  "attrs": {
    "access": "storage[_OWNER_SLOT]",
    "value": "newOwner",
    "slot": "ownerSlot",
    "slot_constant": "_OWNER_SLOT",
    "slot_value": "0xffffffffffffffffffffffffffffffffffffffffffffffffffffffff74873927",
    "storage_model": "manual_constant_slot",
    "state_access": true,
    "state_mutation": true,
    "mutation_kind": "state_write",
    "variable_name_inferred": false,
    "notes": [
      "constant_storage_slot",
      "manual_storage_layout",
      "writes_contract_state"
    ]
  }
}
```

这里不强行命名为某个状态变量，因为 `_OWNER_SLOT` 是手动 storage layout 的常量 slot，不是 Solidity 自动布局中的 state variable。
但语义上它仍然被明确记录为状态读写：`StateVariableWrite` / `state_mutation=true` 表示该 Yul 语句会修改合约状态。
变量名恢复留给后续 Solidity 解混淆阶段处理。

solidity-like 输出会保留固定 slot 表达，同时标注其状态语义：

```solidity
storage[_OWNER_SLOT] = newOwner; /* state write, manual slot */
```

如果固定 slot 读取嵌套在事件参数中，也会在 `EventEmit` 中恢复为状态读取参数，并记录 `argument_state_reads`：

```yul
log3(0, 0, _OWNERSHIP_TRANSFERRED_EVENT_SIGNATURE, sload(ownerSlot), newOwner)
```

其中：

```yul
let ownerSlot := _OWNER_SLOT
```

S-SEIR 记录：

```json
{
  "kind": "EventEmit",
  "attrs": {
    "event": "OwnershipTransferred",
    "args": [
      "storage[_OWNER_SLOT] /* state read, manual slot */",
      "newOwner"
    ],
    "argument_state_reads": [
      {
        "original": "sload(ownerSlot)",
        "access": "storage[_OWNER_SLOT]",
        "slot": "ownerSlot",
        "slot_constant": "_OWNER_SLOT",
        "storage_model": "manual_constant_slot",
        "state_access": true,
        "state_mutation": false,
        "variable_name_inferred": false
      }
    ],
    "notes": ["event_argument_state_read"]
  }
}
```

analysis facts 中会保存常量表：

```text
SSEIRConstantTable:
  _OWNER_SLOT -> 0xffff...74873927
```

常量 slot 表达式同样可以静态折叠。当前支持的 uint256 运算为：

```text
not
add / sub / mul / div / mod
and / or / xor
shl / shr
```

所有运算按 uint256 语义处理；`div/mod` 的除数为零时不折叠。示例：

```yul
sload(not(_ROLE_SLOT_SEED))
```

如果 `not(_ROLE_SLOT_SEED)` 能折叠为已知 constant slot，则记录：

```json
{
  "kind": "StateVariableRead",
  "attrs": {
    "access": "storage[not(_ROLE_SLOT_SEED)]",
    "storage_model": "manual_constant_slot",
    "slot": "not(_ROLE_SLOT_SEED)",
    "slot_constant": "not(_ROLE_SLOT_SEED)",
    "slot_value": "0x...",
    "state_access": true,
    "state_mutation": false,
    "notes": ["constant_storage_slot", "manual_storage_layout", "reads_contract_state"]
  }
}
```

其中内部 constant folding 结果的种类为 `constant_expr_storage_slot`；公开 overlay 统一归档为 `storage_model=manual_constant_slot`。

如果 slot 变量经 ValueDef 指向 Solidity 自动布局中的已知 state variable slot：

```yul
let slotAlias := balance.slot
let value := sload(slotAlias)
```

则记录 `kind=state_variable_slot_alias` 的推导证据，并将访问恢复为：

```text
access = balance
storage_model = direct_state_slot_alias
state_variable = balance
```

该规则既用于独立 `sload`，也用于 condition、event argument 和复合表达式中的嵌套状态读取。

### 6.6 EventEmit

来源：

```text
EventLog
```

判断规则：

```text
parse_events_from_source 解析源码 event 定义。
topic0 必须与事件完整 32 字节 topic0 精确匹配。
如果 topic0 是源码 constant，则先从 SSEIRConstantTable / TypeEnv 解析常量值，再进行事件匹配。
anonymous event 按 topics 数量匹配。
indexed 参数来自 topics，非 indexed 参数来自 data_memory words。
```

未匹配时：

```text
event = unknownEvent
notes 包含 unknown_event_topic0
如果 topic0 前缀接近已知事件但完整值不一致，记录 topic0_near_misses。
```

constant topic0 示例：

```solidity
event OwnershipTransferred(address indexed oldOwner, address indexed newOwner);

uint256 private constant _OWNERSHIP_TRANSFERRED_EVENT_SIGNATURE =
    0x8be0079c531659141344cd1fd0a4f28419497f9722a3daafe3b4186f6b6457e0;
```

Yul：

```yul
log3(0, 0, _OWNERSHIP_TRANSFERRED_EVENT_SIGNATURE, 0, newOwner)
```

S-SEIR 记录：

```json
{
  "kind": "EventEmit",
  "attrs": {
    "event": "OwnershipTransferred",
    "signature": "OwnershipTransferred(address,address)",
    "topic0": "0x8be0079c531659141344cd1fd0a4f28419497f9722a3daafe3b4186f6b6457e0",
    "args": ["0", "newOwner"],
    "raw_topics": ["_OWNERSHIP_TRANSFERRED_EVENT_SIGNATURE", "0", "newOwner"],
    "topic_constants": [
      {
        "name": "_OWNERSHIP_TRANSFERRED_EVENT_SIGNATURE",
        "value": "0x8be0079c531659141344cd1fd0a4f28419497f9722a3daafe3b4186f6b6457e0"
      }
    ],
    "emit_like": "emit OwnershipTransferred(0, newOwner);",
    "notes": ["resolved_topic_constants"]
  }
}
```

indexed topic 内存读示例：

```solidity
event RolesUpdated(address indexed user, uint256 indexed roles);
```

Yul：

```yul
mstore(0x0c, _ROLE_SLOT_SEED)
mstore(0x00, user)
sstore(keccak256(0x0c, 0x20), roles)
log3(0, 0, _ROLES_UPDATED_EVENT_SIGNATURE, shr(96, mload(0x0c)), roles)
```

这里 `mload(0x0c)` 读取的 32 字节并不是单一 word，而是由 MemorySSA 字节轴恢复出的拼接数据：

```text
[0x0c, 0x20) = low_bytes(user, 20) ++ low_bytes(_ROLE_SLOT_SEED, 12)
```

因此对事件第一个 indexed address 参数执行：

```text
shr(96, mload(0x0c))
```

可以去除低 12 字节 seed，恢复为：

```solidity
user
```

S-SEIR 记录：

```json
{
  "kind": "EventEmit",
  "attrs": {
    "event": "RolesUpdated",
    "signature": "RolesUpdated(address,uint256)",
    "args": ["user", "roles"],
    "emit_like": "emit RolesUpdated(user, roles);",
    "argument_memory_reads": [
      {
        "topic_index": 1,
        "param": "user",
        "param_type": "address",
        "raw_expression": "shr(96, mload(0x0c))",
        "resolved": "user",
        "read_ptr": "0x0c",
        "transform": "shr96",
        "memory_read": {
          "byte_slice": {
            "complete": true,
            "packed_semantics": [
              "low_bytes(user, 20)",
              "low_bytes(_ROLE_SLOT_SEED, 12)"
            ]
          }
        }
      }
    ],
    "notes": [
      "event_topic_memory_read_resolved",
      "resolved_topic_constants"
    ]
  }
}
```

该规则仍以 `EventLog` 作为语义终点触发倒推：只有事件 topic 参数内部出现 `mload(ptr)`，并且 MemorySSA 字节轴能完整恢复对应 32 字节来源时才提升参数；否则保留原表达式。

### 6.7 LowLevelCall / StaticCallOverlay / DelegateCallOverlay / PrecompileCall

来源：

```text
Call
StaticCall
DelegateCall
CallCode
```

判断规则：

```text
根据 effect.kind 映射到低层调用 overlay。
target 若是整数地址，转为 address(0x...)。
如果 target 是 Ethereum precompile 地址，则生成 PrecompileCall。
input_memory_partial 可解析 selector 时，用 selector_registry 匹配函数签名。
```

Precompile 处理：

```text
PRECOMPILES 表识别固定地址。
native_precompile_call 可将部分 precompile 调用恢复为 sha256/ripemd160/ecrecover 等 Solidity-like 表达。
如果输入受路径条件影响，则保留 path_conditioned_input，不强行 native lift。
```

普通低层调用示例：

```yul
mstore(ptr, 0xa9059cbb)
mstore(add(ptr, 0x20), to)
mstore(add(ptr, 0x40), amount)
let ok := call(gas(), token, 0, add(ptr, 0x1c), 0x44, 0x00, 0x20)
```

S-SEIR overlay：

```json
{
  "kind": "LowLevelCall",
  "attrs": {
    "target": "token",
    "value": "0",
    "input_ptr": "add(ptr, 0x1c)",
    "input_size": "0x44",
    "output_ptr": "0x00",
    "output_size": "0x20",
    "selector": "0xa9059cbb",
    "selector_signature": "transfer(address,uint256)",
    "solidity_like": "ok = yulCall(gas: gasleft(), target: token, value: 0, input: abi.encodeWithSelector(bytes4(0xa9059cbb) /* transfer(address,uint256) */, to, amount), output: memory[0x00:0x20]);"
  }
}
```

如果 `input_memory.sink_resolution` 在不同 path 上恢复出不同 calldata，则生成路径化调用：

```text
PathConditionedLowLevelCall
PathConditionedStaticCallOverlay
PathConditionedDelegateCallOverlay
PathConditionedPrecompileCall
```

实际 kind 由底层 call kind 和候选 target 决定。每个 candidate 单独保存：

```text
condition
memory_slice
selector / selector_match / selector_signature
arguments
precompile / native_precompile
solidity_like
```

例如同一条 `staticcall` 的输入在两个路径上分别构造为不同 selector：

```json
{
  "kind": "PathConditionedStaticCallOverlay",
  "attrs": {
    "target": "target",
    "input_ptr": "ptr",
    "input_size": "0x24",
    "candidates": [
      {
        "status": "resolved",
        "condition": "modeA",
        "selector": "0x11111111",
        "arguments": ["x"],
        "solidity_like": "ok = yulCall(...);"
      },
      {
        "status": "resolved",
        "condition": "!(modeA)",
        "selector": "0x22222222",
        "arguments": ["y"],
        "solidity_like": "ok = yulCall(...);"
      }
    ],
    "notes": ["path_sensitive_sink_resolution"]
  }
}
```

若所有可恢复候选都指向同一个固定 precompile，则 kind 改为 `PathConditionedPrecompileCall`；每条路径仍保留自己的 input words 和 native projection。

### 6.8 PrecompileOutputRead / PathConditionedPrecompileOutputRead

来源：

```text
PrecompileCall 后续 mload(output_ptr)
```

判断规则：

```text
读取地址必须等于 precompile output_ptr。
读取节点必须发生在 call 后。
中间不能有同地址 memory rewrite。
```

实际例子：

```yul
let ptr := mload(0x40)
mstore(ptr, shl(96, caller()))
let ok := staticcall(gas(), 2, ptr, 20, ptr, 32)
let h := mload(ptr)
```

其中 target `2` 是 Ethereum precompile 地址，当前 `PRECOMPILES` 表会把它识别为 `sha256`。底层 effect 大致是：

```json
[
  {
    "kind": "StaticCall",
    "attrs": {
      "target": "2",
      "input_ptr": "ptr",
      "input_size": "20",
      "output_ptr": "ptr",
      "output_size": "32",
      "input_memory": {
        "words": [
          {
            "value": "shl(96, caller())"
          }
        ]
      }
    }
  },
  {
    "kind": "MemoryRead",
    "attrs": {
      "read_from": "ptr",
      "value": "h"
    }
  }
]
```

先生成 `PrecompileCall`：

```json
{
  "kind": "PrecompileCall",
  "attrs": {
    "precompile": "sha256",
    "input_words": ["(msg.sender << 96)"],
    "native_precompile": {
      "solidity_like": "bytes32 sha256_result_N = sha256(abi.encodePacked(bytes20(msg.sender)));",
      "output_word_expression": "uint256(sha256_result_N)"
    },
    "solidity_like": "bytes32 sha256_result_N = sha256(abi.encodePacked(bytes20(msg.sender)));"
  }
}
```

然后 `precompile_output_overlays()` 再查找后续 `MemoryRead`：

```text
1. MemoryRead.read_from 与 PrecompileCall.output_ptr 相同；
2. MemoryRead 的 cfg_node_id 在 call 的 cfg_node_id 之后；
3. call 与 read 之间没有同 output_ptr 的 MemoryWrite；
4. PrecompileCall.native_precompile.output_word_expression 存在。
```

匹配后生成：

```json
{
  "kind": "PrecompileOutputRead",
  "effects": ["staticcall_effect", "mload_effect"],
  "attrs": {
    "source_precompile_overlay": "ov_precompile",
    "target": "h",
    "value": "uint256(sha256_result_N)",
    "solidity_like": "h = uint256(sha256_result_N);"
  }
}
```

语义说明：

```text
PrecompileCall 表示“调用了固定地址预编译合约”。
PrecompileOutputRead 表示“后续 mload(output_ptr) 读取的是该 precompile 的返回值”。
二者共同把 staticcall + mload 的组合恢复为一个更接近 Solidity 的赋值。
```

如果 precompile call 或其输出指针在不同路径上存在多个 SSA 来源，则生成 `PathConditionedPrecompileOutputRead`，不把候选强行合并：

```json
{
  "kind": "PathConditionedPrecompileOutputRead",
  "attrs": {
    "target": "h",
    "candidates": [
      {
        "status": "resolved",
        "condition": "useSha256",
        "precompile": "sha256",
        "value": "uint256(sha256_result_1)",
        "solidity_like": "h = uint256(sha256_result_1);"
      },
      {
        "status": "resolved",
        "condition": "!(useSha256)",
        "precompile": "identity",
        "value": "identity_result_2",
        "solidity_like": "h = identity_result_2;"
      }
    ]
  }
}
```

只有 `status=resolved` 的 candidate 才带有 `solidity_like` 赋值；若 effect 层传入未解析候选，该候选仍会保留，但不生成赋值文本。

### 6.9 AbiCallDataConstruction / AbiEncodedLowLevelCall

来源：

```text
LowLevelCall / StaticCallOverlay / DelegateCallOverlay
```

判断规则：

```text

selector_source
selector_write_effect
selector_match
signature
head_words
arguments

```


### 6.10 MemoryRegionAllocate / MemoryRegionWrite

来源：

```text
mload(0x40)
mstore(0x40, newFreePointer)
两者之间写入 mload(0x40) 派生内存区域的数据
```

判断规则：

```text
manual_memory_allocations 找最近的 mload(0x40) 与后续 mstore(0x40, value)。
memory_writes_inside_allocation 只收集分配区间内、非 0x40、非返回 struct 接收体字段的内存写。
地址 alias base 必须是 mload(0x40) 或 add(mload(0x40), ...)。
```

与 MemoryRead / MemoryWrite 的关系：

```text
MemoryRegionAllocate / MemoryRegionWrite 不替代 MemoryWrite，也不会删除底层 MemoryWrite。
它们是叠加在 MemoryWrite 之上的高级解释层。
```

去重规则：

```text
MemoryRegionAllocate 可能因 SSA/path 版本产生多条等价 overlay。
当前按语义 key 去重，而不是按 effect_id 去重。
```

语义 key 包括：

```text
kind
base
new_free_pointer
start_node
end_node
stmt_refs
```

去重后：

```text
只保留一条 MemoryRegionAllocate。
effects / stmt_refs / path_states 合并保留。
merged_effects 记录被合并的证据来源。
```

也就是说，同一条 Yul：

```yul
mstore(logs, n)
```

可以同时在模型中出现：

```text
Effect: MemoryWrite(address=logs, value=n)
Overlay: MemoryRegionWrite(region_base=mload(0x40), address=logs, value=n)
```

这不是冲突，而是两层语义：

```text
MemoryWrite 表示“某个地址被写入了 n”。
MemoryRegionWrite 表示“这个写入属于一次 free-memory-pointer 手工分配出来的内存区域”。
```

实际例子：

```yul
let logs := add(mload(0x40), 0x40)
mstore(logs, n)
let offset := add(0x20, logs)
mstore(0x40, add(offset, shl(5, n)))
```

底层仍记录：

```json
{
  "kind": "MemoryWrite",
  "attrs": {
    "address": "logs",
    "value": "n"
  }
}
```

同时高级层记录：

```json
{
  "kind": "MemoryRegionAllocate",
  "attrs": {
    "base": "mload(0x40)",
    "new_free_pointer": "(offset + (n << 5))",
    "stored_values": [
      {
        "address": "logs",
        "value": "n"
      }
    ]
  }
}
```

如果这些写入还能匹配返回 struct 字段，则还会进一步出现 `StructInitializationFragment`。因此它和普通内存读写不是互斥关系，而是：

```text
MemoryWrite -> MemoryRegionWrite -> StructInitializationFragment
```

逐层提高语义抽象。

### 6.15 RawReturnData

来源：


判断规则：

```text
只依赖 Yul Return effect 本身。
Return 被视为 memory 语义终点。

```

这条高级语义不要求前面必须存在某种固定形式的 `mstore`。
`mstore` 只是 MemoryWrite effect；它是否成为 return payload 的来源，由 Return sink 的 MemorySSA 查询结果决定。

```text
  payload_size

  values
  words
  partial_slices
  solidity_like
  solidity_equivalent = false
  reason = yul_return_terminates_current_evm_call_with_raw_return_data
  path_states
```

### 6.18 AddressZeroCheck

来源：

```text
Branch effect
ValueDef SSA
TypeEnv
```

目的：

```text
识别 Yul 中针对 address 值的零地址检查，将低层位运算/比较条件提升为明确的 address zero-check 语义。
当前只新增语义 overlay，不改写原有 Branch / Revert / solidity-like 求值链。
```

触发点：

```text
只在 Branch 条件语义终点触发。
不全局扫描普通表达式，避免把无控制语义的位运算误判为地址检查。
```

判断规则：

```text
1. 识别 zero-check 外壳：
   iszero(x)
   eq(x, 0)
   eq(0, x)
   iszero(iszero(x))
   iszero(eq(x, 0))

2. 识别 address projection：
   addressVar
   shl(96, addressVar)
   shr(96, shl(96, addressVar))
   and(addressVar, 0xffffffffffffffffffffffffffffffffffffffff)

3. 如果 x 是临时变量，则通过 ValueDef SSA 继续追踪：
   clean -> shr(96, shl(96, account))

4. 最终变量必须能通过 TypeEnv 确认为 address 类型。
```

输出语义：

```text
iszero(address_projection)       -> addressVar == address(0)
eq(address_projection, 0)        -> addressVar == address(0)
iszero(iszero(address_projection))-> addressVar != address(0)
iszero(eq(address_projection,0))  -> addressVar != address(0)
```

S-SEIR 示例：

```json
{
  "kind": "AddressZeroCheck",
  "attrs": {
    "variable": "newOwner",
    "variable_type": "address",
    "check": "is_zero",
    "condition": "newOwner == address(0)",
    "source_expression": "iszero(shl(96, newOwner))",
    "source_pattern": "iszero(address_projection)",
    "projection": "shl(96, address)",
    "projection_expression": "shl(96, newOwner)",
    "via_value_defs": [],
    "used_by": "Branch",
    "solidity_like": "newOwner == address(0)",
    "solidity_equivalent": true
  }
}
```

实际样例：

```solidity
function transferOwnership(address newOwner) public payable virtual onlyOwner {
    assembly {
        if iszero(shl(96, newOwner)) {
            mstore(0x00, 0x7448fbae)
            revert(0x1c, 0x04)
        }
    }
    _setOwner(newOwner);
}
```

S-SEIR 恢复：

```text
AddressZeroCheck:
  source_expression = iszero(shl(96, newOwner))
  condition = newOwner == address(0)

CustomErrorRevert:
  selector = 0x7448fbae
  error = NewOwnerIsZeroAddress()
```

测试样例：

```text
iszero(shl(96, newOwner))
  -> newOwner == address(0)

eq(recipient, 0)
  -> recipient == address(0)

iszero(iszero(shl(96, target)))
  -> target != address(0)

let clean := shr(96, shl(96, account))
if iszero(clean)
  -> account == address(0)

eq(and(spender, 0xffffffffffffffffffffffffffffffffffffffff), 0)
  -> spender == address(0)
```

Expression Role 补充：

```text
address_zero_checked_value:
  被检查的 address 变量。

guard_condition:
  normalized 记录为 addressVar == address(0) 或 addressVar != address(0)。
```

### 6.19 手工 packed hash 状态槽

来源：

```text
MemoryHash effect
MemoryByteAxis byte_slice
StorageRead / StorageWrite consumer
```

目的：

```text
恢复通过非对齐/重叠 memory 写入构造出来的 keccak256 storage slot。
这类 slot 往往不是普通 mapping slot 的 abi.encode(key, slot) 形式，而是手写 packed hash slot。
```

触发规则：

```text
1. MemoryHash 的 memory_read 中存在完整 byte_slice。
2. byte_slice.slices 可以合并为确定的 packed_semantics。
3. 该 MemoryHash 被后续 sload / sstore 消费。
4. 不满足普通 MappingSlot 规则时，将其作为 StateVariableRead / StateVariableWrite 的 slot_derivation 记录。
```

单个完整 32-byte word 不会自动标记为 packed hash：

```yul
mstore(0x00, x)
let h := keccak256(0x00, 0x20)
```

仅凭这一组操作，当前规则不会猜测源码意图是 `keccak256(abi.encode(x))`、某个自定义 slot，还是单纯对原始 32 字节求哈希。
若该 hash 被 storage sink 消费但没有匹配已知 storage 模式，则路径候选记录：

```text
status = unresolved
reason = single_word_hash_not_packed_slot_pattern
resolved_inputs = [x]
```

当前只对一个明确的单 word packed 子模式做展开：

```yul
mstore(ptr, or(shl(96, account), seed))
keccak256(ptr, 0x20)
```

该 word 可无歧义拆为：

```text
bytes20(account) ++ low_bytes(seed, 12)
```

因此记录为：

```solidity
keccak256(abi.encodePacked(bytes20(account), low_bytes(seed, 12)))
```

普通 mapping 的 64-byte `key + baseSlot` 模式仍记录为 `keccak256(abi.encode(key, baseSlot))`，不与该 packed 子模式混用。

S-SEIR 记录：

这里不再单独输出 `ManualPackedHashSlot` 作为高级 overlay。因为该语义本质仍然是状态读写，只是 slot 的来源不是常规 Solidity storage layout。

如果该 slot 被 `sstore` 消费，则生成 `StateVariableWrite`，并在其中附带 `slot_derivation`：

```json
{
  "kind": "StateVariableWrite",
  "attrs": {
    "access": "storage[keccak256(abi.encodePacked(bytes20(msg.sender), low_bytes(_HANDOVER_SLOT_SEED, 12)))]",
    "value": "expires",
    "storage_model": "manual_packed_hash_slot",
    "state_access": true,
    "state_mutation": true,
    "mutation_kind": "state_write",
    "variable_name_inferred": false,
    "slot_derivation": {
      "kind": "manual_packed_hash_slot",
      "hash": "keccak256",
      "encoding": "abi.encodePacked",
      "expression": "storage[keccak256(abi.encodePacked(bytes20(msg.sender), low_bytes(_HANDOVER_SLOT_SEED, 12)))]",
      "packed_inputs": [
        "bytes20(msg.sender)",
        "low_bytes(_HANDOVER_SLOT_SEED, 12)"
      ],
      "notes": [
        "manual_packed_hash_slot",
        "byte_axis_memory_slice"
      ]
    }
  }
}
```

如果该 slot 被 `sload` 消费，则生成 `StateVariableRead`，字段结构相同，只是 `state_mutation=false`，并通过 `target` 记录读取结果变量。

实际样例：

```solidity
function requestOwnershipHandover() public payable virtual {
    unchecked {
        uint256 expires = block.timestamp + _ownershipHandoverValidFor();
        assembly {
            mstore(0x0c, _HANDOVER_SLOT_SEED)
            mstore(0x00, caller())
            sstore(keccak256(0x0c, 0x20), expires)
            log2(0, 0, _OWNERSHIP_HANDOVER_REQUESTED_EVENT_SIGNATURE, caller())
        }
    }
}
```

solidity-like 输出：

```solidity
assembly /* s-seir solidity-like view */ {
    memory[0x0c] = _HANDOVER_SLOT_SEED;
    memory[0x00] = msg.sender;
    storage[keccak256(abi.encodePacked(bytes20(msg.sender), low_bytes(_HANDOVER_SLOT_SEED, 12)))] = expires;
    emit OwnershipHandoverRequested(msg.sender);
}
```

这里仍不推断高级变量名，只记录：

```text
这是一个由 packed memory 构造的 hash slot；
它被用于状态写入；
具体源码变量命名留给后续 Solidity 解混淆/LLM 阶段。
```

### 6.20 BytesContentHash：动态 bytes/string 内容哈希

来源：

```text
MemoryHash effect
ValueDef SSA 链
Solidity TypeEnv
```

目标模式：

```yul
let dataPtr := add(data, 0x20)
let dataSize := mload(data)
let digest := keccak256(dataPtr, dataSize)
```

记录方法：

```text
1. 以 MemoryHash 为语义终点，分别追踪 ptr 和 size 的 SSA 来源。
2. 每个操作数必须能得到唯一的、覆盖该 sink 全部可达路径的定义链。
3. TypeEnv 必须确认 base object 是 bytes memory 或 string memory。
4. ptr 必须匹配 object + 32，size 必须匹配 mload(object)。
5. 条件分支造成多个不等价定义时，不生成 BytesContentHash，保留 MemoryHash。
```

该规则不会因为 assembly 内没有 `mstore` 就拒绝恢复。`bytes memory` 或 `string memory`
对象可以由 Solidity 创建，其数据布局由类型和 `object + 32 / mload(object)` 共同证明。

记录示例：

```json
{
  "kind": "BytesContentHash",
  "effects": ["eff_ptr", "eff_size", "eff_hash"],
  "stmt_refs": ["asm_s_1", "asm_s_2", "asm_s_3"],
  "attrs": {
    "object": "data",
    "object_type": "bytes memory",
    "data_pointer": "add(data, 0x20)",
    "length_expression": "mload(data)",
    "target": "digest",
    "expression": "keccak256(data)",
    "result_expression": "keccak256(data)",
    "via_value_defs": ["eff_ptr", "eff_size"],
    "hash_algorithm": "keccak256",
    "pattern": "dynamic_bytes_memory_data_pointer_and_length",
    "exact_solidity_equivalent": true,
    "solidity_like": "digest = keccak256(data);"
  }
}
```

对于 `string memory text`，结果记录为：

```solidity
digest = keccak256(bytes(text));
```

### 6.22 路径化 storage candidate 与等价 SSA 合并

当同一条 `sload/sstore` 在不同控制路径上接收到多个 slot SSA 版本时，不应提前把同名变量合并。
Storage overlay 先为每个版本建立候选项：

```text
PathConditionedStorageRead
PathConditionedStorageWrite
```

每个 candidate 至少记录：

```text
slot_key
status: resolved / unresolved
condition
overlay_kind
access
state_variable / key / value
unresolved_reason
```

示例：

```json
{
  "kind": "PathConditionedStorageWrite",
  "attrs": {
    "slot_versions": ["toSlot__ssa9", "toSlot__ssa10", "toSlot__ssa11"],
    "value": "amount",
    "candidates": [
      {
        "status": "resolved",
        "condition": "pathA",
        "access": "balances[to]",
        "slot_keys": ["toSlot__ssa9", "toSlot__ssa10"],
        "merged_candidate_count": 2,
        "notes": ["equivalent_ssa_storage_candidates_merged"]
      },
      {
        "status": "unresolved",
        "condition": "pathB",
        "access": "storage[toSlot__ssa11]",
        "unresolved_reason": "unknown_storage_slot_version"
      }
    ]
  }
}
```

等价合并只发生在高级语义投影完成之后，且以下字段完全相同：

```text
status、condition、overlay_kind、access、target、value、state_variable、key、
result_type、terminal_storage_value、storage_model、unresolved_reason
```

合并时保留所有 `slot_keys`、`slot_effects` 和合并计数。以下内容绝不合并：

```text
不同 condition 的候选；
resolved 与 unresolved 候选；
访问对象或写入值不同的候选。
```

因此该去重只消除“不同 SSA/path 版本表达同一语义”的重复，不会丢掉分支语义。

### 6.23 Selector、Custom Error 与 Event 的证据规则

Selector registry 从 Solidity AST 收集函数和 custom error 的规范签名，并计算 4-byte selector。
调用、revert 等 overlay 的 selector 记录结构为：

```json
{
  "selector": "0x82b42900",
  "selector_source": "0x82b42900",
  "preferred_kind": "error",
  "best_match": {
    "kind": "error",
    "name": "Unauthorized",
    "signature": "Unauthorized()"
  },
  "matches": [
    {
      "kind": "error",
      "name": "Unauthorized",
      "signature": "Unauthorized()",
      "source": "ast"
    }
  ],
  "match_status": "matched"
}
```

规则：

```text
1. selector 必须来自可追踪的常量、memory slice 或 ABI calldata 构造结果。
2. registry 保留全部碰撞匹配项，best_match 优先采用当前语义期望的 kind。
3. 未匹配时保留 selector 和 match_status=unmatched，不编造函数或 error 签名。
4. 源码注释中的 `name(types)` 只有在重新计算后与字面 selector 完全一致时，才可作为证据。
```

Event 的规则更严格：

```text
非 anonymous event：topic0 必须与 keccak256(EventSignature) 的完整 32 bytes 相等，
并且 topic 数量必须等于 indexed 参数数量 + 1。

anonymous event：只能按 anonymous 定义及 indexed topic 数量匹配。

仅前缀相似不恢复为已知事件。前 4 bytes 以上相似只记录
topic0_near_misses，EventEmit.event 仍为 unknownEvent。
```

near-miss 示例：

```json
{
  "kind": "EventEmit",
  "attrs": {
    "event": "unknownEvent",
    "signature": null,
    "topic0": "0x8c5be1e5...different_tail",
    "topic0_near_misses": [
      {
        "event": "Approval",
        "signature": "Approval(address,address,uint256)",
        "matching_prefix_nibbles": 8,
        "reason": "event_topic0_requires_full_32_byte_match"
      }
    ]
  }
}
```

### 7.4 角色不是新语义，而是索引层

Expression Role 不会替代 effect 或 overlay。它的作用是把某个表达式在当前语义中的用途标出来，方便后续查询和 LLM 消费。

例如同一个表达式 `o` 可以有多个角色：

```text
在 call 中：o 是 call_output_ptr
在 mload(o) 中：o 是 memory_slice_start
在 ABI calldata 构造中：o 是 calldata base 的一部分
```

这不是冲突，而是同一表达式在不同语义节点中的不同用途。

例子：`DN404._packedLogsSend` 中的调用数据构造。

```yul
let logs := mload(p)
let o := sub(logs, 0x40)
mstore(o, 0x263c69d6)
mstore(add(o, 0x20), 0x20)
let n := add(0x44, shl(5, mload(logs)))
call(gas(), mirror, 0, add(o, 0x1c), n, o, 0x20)
```

相关 role 会把这些表达式分别标为：

```text
p       -> struct_field_ptr / memory_slice_start
logs    -> struct_field_value，语义上可对应 p.logs
add(o, 0x1c) -> call_input_ptr / abi_calldata_ptr
n       -> call_input_size / abi_calldata_size
0x263c69d6 -> abi_selector
logs    -> abi_argument，value_semantic = p.logs
mirror  -> call_target
o       -> call_output_ptr
```

后续 LLM 不需要重新猜 `add(o, 0x1c)` 为什么是 calldata 起点，也不需要从 `mstore(o, selector)` 手动反推 selector；这些用途已经在 role 与 overlay 中记录。

```text
solidity-like 会从 effect/overlay 的 path_states 中恢复语句所在 condition。
相邻且文本完全相同的 if(condition) 块会做展示层合并。
循环会根据 control 中的 loop-condition / loop-post / loop-body 信息尽量恢复为 for/while 结构。
```

### 10.1 Loop Exit Guard 的展示规则

循环后的语句可能在 CFG 路径枚举中携带 loop exit 条件，例如：

```yul
for { let t := roles } 1 {} {
    mstore(ptr, o)
    ptr := add(ptr, shl(5, and(t, 1)))
    o := add(o, 1)
    t := shr(o, roles)
    if iszero(t) { break }
}
mstore(ordinals, shr(5, sub(ptr, add(ordinals, 0x20))))
mstore(0x40, ptr)
```

从 CFG 到达循环后继节点的路径可以表示为：

```text
1 && iszero(t)
```

但这里的 `iszero(t)` 是退出循环的边条件，不是后继两条 `mstore` 自己所属的 `if` 条件。因此 solidity-like 投影时会：

```text
1. 从 control layer 识别 loop-condition、loop body、loop 后继区域；
2. 从 ControlTransfer(break) 和循环条件中收集 loop exit predicates；
3. 对位于 loop 后继区域的语句，删除这些 loop exit predicates；
4. 保留外层真实分支条件，例如 outer && loop_exit 只简化为 outer。
```

修正后的输出示例：

```solidity
while (true) {
    memory[ptr] = o;
    ptr = (ptr + ((t & 1) << 5));
    o = (o + 1);
    t = (roles >> o);
    __sseir_eval_asm_s_10_1 = (t == 0);
    if (__sseir_eval_asm_s_10_1) {
        break;
    }
}
memory[ordinals] = ((ptr - (ordinals + 0x20)) >> 5);
memory[0x40] = ptr;
```

如果循环整体位于外层条件中，则外层条件仍会保留：

```text
outer && 1 && iszero(t)
→ outer
```

### 10.2 静态恒真循环的展示规则

S-SEIR 的 control layer 仍保留原始 Yul 条件：

```json
{
  "terminator": {
    "kind": "Branch",
    "text": "for condition 1",
    "node_kind": "loop-condition"
  }
}
```

solidity-like 只在静态分析能够保守确认恒真时展示为：

```solidity
while (true) {
    ...
}
```

当前确认范围：

```text
true
非零整数字面量，例如 1 / 0x1
```

不会对符号表达式或复杂恒真表达式做激进判断。例如：

```yul
for { } lt(i, n) { } { ... }
```

仍展示为：

```solidity
for (; (i < n); ) {
    ...
}
```

### 10.3 多 condition 的 DNF 简化与条件树展示

`path_states` 仍以完整条件保存在 S-SEIR 中。展示层会把同一语句的多个可达条件视为 DNF：

```text
(A && B) || (A && C) || (!A && D)
```

处理规则：

```text
1. 按顶层 || 拆为 term，再按顶层 && 拆为 condition atom。
2. 删除同时包含 X 与 !X 的不可满足 term。
3. 执行集合吸收：若一个 term 是另一个 term 的子集，删除更长的冗余 term。
4. 合并精确互补路径：A && B 与 !A && B 合并为 B。
5. 执行受限互补吸收：A || (!A && B) 化简为 A || B。
6. 不证明任意表达式之间的逻辑等价，只识别显式的同一 atom 及其否定。
```

若化简后仍有多个 term，展示层按共同 atom 建立条件树。例如：

```text
(A && B) || (A && C)
```

展示为：

```solidity
if (A) {
    if (B) {
        statement;
    }
    if (C) {
        statement;
    }
}
```

若完整的正反路径都到达同一条语句：

```text
(A && B) || (!A && B)
```

则展示为：

```solidity
if (B) {
    statement;
}
```

当全部条件互补后结果为空，说明语句在该合流点无条件执行，展示层不再生成 `if`。

该过程只修改 solidity-like 的缩进和结构。原始 `path_states`、effect、overlay、SSA 版本均保持不变。
相邻且“渲染文本与化简后条件”都完全相同的语句块才允许做展示去重；语义、写入值或条件不同的语句不会合并。

## 11. 当前模型边界

当前实现已经能统一记录：

```text
基础 Yul 表达式归一
Yul AST 复合右值原子化与从右到左求值顺序
MemorySSA / lazy memory query
MemoryByteAxis / overlapping memory write recovery
线性 memory alias / known-value / function-level assembly bridge
storage slot / mapping / state variable 读写
路径化 storage SSA candidate 与等价语义去重
manual packed hash slot
condition-revert require
address zero-check
address.code.length / address has-code
bytes/string 内容哈希
event log
low-level call / precompile / ABI calldata 构造
call output / returndata pointer def-use
calldata word 读取
局部 memory allocation
memory struct 初始化片段
memory struct 字段读写与 cursor 写入
function-level Solidity/Yul CFG 融合
solidity-like 审计视图
```

当前仍应视为语义模型和审计视图，而不是完整 Solidity 反编译器：

```text
部分 Yul 语义没有无损 Solidity 等价物，例如 storage pointer .slot 绑定、手动 memory layout、原样转发 revert bytes。
复杂 ABI 类型、复杂 alias、复杂循环内存构造仍可能保留为 summary / unknown / unresolved。
security_facts 是辅助摘要，后续 LLM 恢复源码时不必强依赖。
```

## 12. 当前 Pipeline 的完整记录顺序

S-SEIR 不是把各模块最终文本拼接到一起，而是按以下顺序逐层增加证据和语义：

### 12.1 Pass 0：分支预处理与编译输入

```text
输入：原始 Solidity 源码及可解析 imports
处理：branch preprocess、必要的 import flatten、solc AST 编译
输出：analysis_source、Solidity/Yul AST、SSEIRBranchPreprocess fact
```

分支预处理发生在正式分析之前。后续 `stmt_refs`、CFG 和 SSA 统一对应 `analysis_source`，同时保留 `original_source` 路径供审计对照。

### 12.2 Pass 1：函数上下文与 Source Statement Table

```text
SourceStatementCollector
Storage layout application
TypeEnv
```

该阶段以函数为处理单位，收集 Solidity 与函数内全部 assembly 语句，建立参数、返回值、局部变量、状态变量、struct、constant 和类型环境。

### 12.3 Pass 2：Function-level Control Layer

```text
ControlBuilder = Slither Solidity CFG + assembly AST CFG
```

Solidity block 使用 Slither CFG 的结构，assembly 子图使用 Yul AST CFG，并在 assembly 入口/出口与所属 Solidity block 之间建立边。
后续 `path_states`、loop、branch 和 sink 可达性均以该函数级 control graph 为依据。

### 12.4 Pass 3：MemorySSA 查询视图

```text
build_memory_ssa_views(unit, control)
```

该阶段建立：

```text
每个 assembly block 的 MemorySSA backend；
线性地址 alias；
known-value 信息；
byte-axis 重叠写入模型；
LoopMemoryRecord / lazy materialization；
受限的 function-level 多 assembly memory bridge。
```

MemorySSA 的职责是提供查询证据，不直接生成 Solidity 高级语义。

### 12.5 Pass 4：初始 Expression Roles

```text
ExpressionRoleAnalyzer(unit, type_env, memory_ssa)
```

先按 Yul AST 和类型环境标注基础用途，例如 free-memory pointer、call 参数、revert/return payload、memory slice 和 loop bound。

### 12.6 Pass 5：Effect Lifting 与表达式原子化

```text
EffectLifter(unit, memory_ssa, control)
```

该阶段：

```text
将 Yul 操作提升为 Memory/Storage/Call/Event/Revert/Return 等 effect；
按 Yul/EVM 从右到左求值顺序原子化复合右值；
为嵌套 sink 建立独立 effect 和 EvaluationStep；
将 MemorySSA 查询结果挂到消费它的 sink；
建立 call output 与后续 memory read 的 def-use。
```

### 12.7 Pass 6：Branch Materialization

```text
build_branch_materialization_nodes(unit, memory_ssa)
```

该阶段记录不同 condition 下的 SSA/memory 来源，并为受分支影响的语义终点保留路径化候选。
它不会把多个候选提前压成一个值。

### 12.8 Pass 7：SinkResolver 与 Semantic Overlay

Overlay Builder 首先执行：

```text
SinkResolver.attach_all(effects)
```

随后按实际代码顺序构建 overlay：

```text
Require / AddressZeroCheck
RawRevertBytes / BytesContentHash / Return
CustomError
Storage
Event
Call / Precompile output
DivisionGuard
Memory object / struct mutation
ABI calldata
CalldataWordRead / AddressCode
Memory array read / construction
ExpressionNormalization
```

这一顺序允许后面的 overlay 使用前面已经建立的底层 effect 与高级语义证据。例如 ABI calldata overlay 可以同时使用 Call effect、SinkResolver 结果和 memory construction overlay。

### 12.9 Pass 8：Semantic Normalization

```text
SemanticNormalizer
```

该阶段统一补充 Expression Role，生成 `SemanticSinkMemoryQuery`、未解析事实和 branch materialization 事实。
它不会重新解释 opcode，也不会用 role 覆盖原 effect。

### 12.10 Pass 9：辅助表、Security Facts 与导出

依次补充：

```text
SSEIRStructTable
SSEIRConstantTable
SSEIRSelectorRegistry
SSEIRBranchPreprocess
SecurityFactBuilder
```

最终构造 `FunctionSSEIR`。标准 JSON 保存完整模型；solidity-like、LLM assembly、CFG DOT 都是从该模型生成的不同投影视图。

## 13. 保守记录总原则

### 13.1 Effect 不因高级语义成功而删除

例如 `MappingWrite` 成功恢复后，原 `MemoryWrite`、`MemoryHash` 和 `StorageWrite` 仍保留。Overlay 通过 `effects` 引用证据，而不是替换证据。

### 13.2 高级语义必须由完整模式支持

```text
mapping 必须由 storage sink、hash 输入和 storage layout 共同支持；
bytes hash 必须同时匹配 data pointer、length 和 Solidity 类型；
event 必须完整匹配 topic0 和 topic 数量；
custom error/function 必须匹配 selector registry 或通过校验的源码签名；
ABI call 必须能恢复出相应 input memory range。
```

只匹配到模式的一部分时，保留底层 effect 或 unresolved candidate，不猜测缺失部分。

### 13.3 SSA、condition 和 unknown 均作为证据保留

```text
同名变量的不同 SSA 版本不能只按变量名合并；
不同 condition 下的候选分别记录；
只有 condition 和高级语义都相同的 resolved candidate 才允许去重；
未知路径保留 unknown/unresolved，不强行借用另一条路径的值。
```

### 13.4 MemorySSA 是主查询层，SinkResolver 是补充层

查询优先使用 MemorySSA、byte axis 和 loop lazy result。SinkResolver 只在 sink 局部补充跨表达式、切片或 call-output 关系。
SinkResolver 恢复成功不会删除 MemorySSA 查询，也不会使原 `memory_query_has_unknown` 消失。

### 13.5 `known` 表示来源可信，不表示数值可求值

常量、标准 EVM builtin、简单标识符、`.slot` 表达式和未显式 unknown 的复合表达式均可标记为 known。
这只表示 MemorySSA 保存了可继续追踪的符号表达式；例如 `msg.sender` 是 known symbolic value，但不是静态常量地址。
变量是否真是参数、返回值、状态变量，以及该表达式能否提升为高级语义，仍必须由 TypeEnv 和 overlay 完整模式验证。

### 13.6 Solidity-like 不反向修改 S-SEIR

条件树、互补条件化简、相邻块合并、helper 表达式和缩进均属于展示规则。
它们不能改变 control edges、`path_states`、effect、overlay 或 SSA evidence。无法无损表达的 Yul 语义允许保留 assembly-like/helper 形式。
