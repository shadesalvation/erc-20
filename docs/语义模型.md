# S-SEIR 语义模型当前实现说明

本文只总结当前代码中已经实际实现的 S-SEIR 语义模型，依据的主要文件包括：

```text
scripts/s_seir/s_seir_model.py
scripts/s_seir/s_seir_pipeline.py
scripts/s_seir/s_seir_control_builder.py
scripts/s_seir/s_seir_memory_ssa.py
scripts/s_seir/s_seir_effect_lifter.py
scripts/s_seir/s_seir_overlay_builder.py
scripts/s_seir/s_seir_semantic_normalizer.py
scripts/s_seir/s_seir_security_facts.py
scripts/s_seir/s_seir_solidity_like_export.py
```

## 1. 函数级输出结构

当前 S-SEIR 以函数为单位输出。`FunctionSSEIR.to_dict()` 中真实存在的字段是：

```text
function_id
contract
function
signature
source_statements
control
expr_roles
effects
semantic_overlays
security_facts
analysis_facts
```

目前代码中没有单独输出 `projection_policies` 层。可否恢复为 Solidity 的判断主要体现在 `semantic_overlays[*].attrs.solidity_like`、`reason`、`unresolved_reason`，以及 `solidity-like` 导出视图中。

## 2. Source Statements

`source_statements` 保存原始 Solidity / Yul 语句。后续所有 effect、overlay、fact 都通过 `stmt_refs` 回指原语句。

典型字段：

```text
stmt_id
lang
text
src
function_id
block_id
origin
```

判断规则：

```text
SourceStatementCollector 从 solc AST 中提取函数内 Solidity 语句与 inline assembly/Yul 语句，并给每条语句分配 stmt_id。
```

## 3. Control 层

`control` 是函数级 CFG。当前实现采用混合方式：

```text
Solidity 函数 CFG：优先使用 Slither function.nodes
Yul CFG：使用本项目原 assembly_ast_cfg.build_yul_cfg
拼接策略：将 Slither 中 assembly 范围内的节点替换为本地 Yul CFG 子图
```

实际记录：

```text
blocks
edges
notes
loop_contexts
```

其中 block 分为：

```text
kind = solidity
kind = yul
```

terminator 支持：

```text
Branch
Return
Revert
Stop
Terminal
Fallthrough
YulNode
```

循环上下文：

```text
ControlBuilder 会从 solc AST 中识别 Solidity 的 ForStatement / WhileStatement / DoWhileStatement。
如果 assembly 块位于这些 loop 范围内，则在 control.loop_contexts 中给该 assembly_block 附加 function-level loop context。
```

如果 Slither 不可用，则退化为 Solidity 顺序骨架 + Yul CFG 子图。

## 4. MemorySSA 查询层

当前 S-SEIR 的 MemorySSA 不是完全重写的新算法，而是：

```text
S-SEIR 持有 SSeirMemorySSAView
底层复用原 assembly_memory_ssa.analyze_block
查询时复用 assembly_cfg_memory_adapter.resolve_memory_read_with_loops
```

S-SEIR 在查询结果上补充：

```text
owner = S-SEIR
tracker_scope = s_seir_memoryssa_query
assembly_block
function_loop_context
loop_alignment
inside_function_level_loop
```

实际保留的关键能力：

```text
path_states
linear_aliases
branch_candidates
loop_phi_facts
range_summary_facts
memory_top_facts
lazy memory query
```

MemorySSA 相关 analysis_facts：

```text
MemorySSAQueryLayer
LoopMemoryRecord
MemoryPhi
MemoryRangeSummary
MemoryTop
SemanticSinkMemoryQuery
```

## 5. Effect 层：低层语义

Effect Layer 记录“发生了什么底层操作”，不直接解释成高级 Solidity 语义。

### 5.1 ValueDef

来源：

```text
Yul variable declaration / assignment
```

记录：

```text
targets
value
value_normalized
target_versions
cfg_node_id
path_states
```

示例：

```yul
let o := sub(logs, 0x40)
```

对应：

```text
kind = ValueDef
targets = ["o"]
value = sub(logs, 0x40)
value_normalized = (logs - 0x40)
```

### 5.2 MemoryWrite

来源：

```text
MemorySSA 中记录到的 mstore / mstore8 等 memory definition
```

记录：

```text
address
value
memory_version
origin_node
write_kind
aliases
cfg_node_id
path_states
```

其中 `aliases` 是线性地址别名结果，例如：

```text
add(o, 0x20) -> base=o, offset=32
```

### 5.3 MemoryRead

来源：

```text
mload(ptr)
```

记录：

```text
read_from
value
value_versions
memory_read
path_states
```

判断规则：

```text
遇到 mload 语义终点时，调用 MemorySSA 查询层。
如果该 mload 读取的是刚刚 call/staticcall 输出的 output_ptr，会将读取结果标注为 call_output_word(call_temp, 0)。
```

### 5.4 MemoryHash

来源：

```text
keccak256(ptr, size)
sload/sstore 参数中内联出现的 keccak256(ptr, size)
```

记录：

```text
ptr
size
value
value_versions
memory_read
inline_storage_slot
```

判断规则：

```text
只有 keccak256 作为语义终点或 storage slot 来源时，才触发 memory backward tracking。
```

### 5.5 MemoryCopy

来源：

```text
calldatacopy
codecopy
returndatacopy
mcopy
extcodecopy
```

记录：

```text
op
args
cfg_node_id
path_states
```

### 5.6 StorageRead / StorageWrite

来源：

```text
sload(slot)
sstore(slot, value)
```

记录：

```text
slot
slot_versions
value
value_versions
cfg_node_id
path_states
```

判断规则：

```text
slot 使用 SSA 版本追踪。
如果 slot 来自 keccak256，则会激活对应 MemoryHash 参与后续 MappingSlot / MappingRead / MappingWrite 恢复。
```

### 5.7 Call / StaticCall / DelegateCall / CallCode

来源：

```text
call
staticcall
delegatecall
callcode
```

记录：

```text
op
args
gas
target
value
input_ptr
input_size
output_ptr
output_size
input_memory
input_memory_partial
output_memory_query
result
path_states
```

判断规则：

```text
EffectLifter 从 Yul call 参数中提取调用元数据。
input_ptr/input_size 作为 memory sink 触发 calldata 构造追踪。
```

### 5.8 EventLog

来源：

```text
log0-log4
```

记录：

```text
op
data_ptr
data_size
topics
data_memory
path_states
```

判断规则：

```text
topics 直接来自 log 参数。
data_ptr/data_size 通过 MemorySSA 查询 memory words。
```

### 5.9 Branch / EvaluationStep

`Branch` 来源：

```text
YulIf
Solidity if 语句
```

Yul Branch 记录：

```text
condition
condition_normalized
condition_evaluation
condition_final_temp
path_states
```

`EvaluationStep` 来源：

```text
Yul if 条件表达式中的复杂函数调用链
```

判断规则：

```text
使用 Yul AST 解析条件表达式。
按 Yul/EVM dialect 函数参数从右到左求值的顺序生成临时变量步骤。
```

示例：

```yul
if iszero(and(eq(mload(o), 1), call(...))) { ... }
```

会被拆成若干 `EvaluationStep`，最后 `Branch.condition_final_temp` 指向最终临时变量。

### 5.10 Revert / Return / ControlTransfer

`Revert` / `Return` 来源：

```text
Yul revert(ptr, size)
Yul return(ptr, size)
Solidity revert / return
```

Yul 记录：

```text
payload_ptr
payload_size
payload_memory
payload_memory_partial
path_states
```

`ControlTransfer` 来源：

```text
break
continue
leave
```

## 6. Semantic Overlay 层：高级语义

Overlay Layer 将低层 effect 解释为高级语义。

### 6.1 RequireOverlay

来源：

```text
revert(0, 0)
除法 / 取模表达式的除零保护
```

判断规则：

```text
revert(0,0) 会查找最近或可合并的 path condition，并取反生成 require(condition)。
如果上层 condition 块内存在其他有效副作用，则停止向上合并，只使用最近可合并条件。
div/mod 相关表达式通过 division_guards 生成 require(divisor != 0)。
```

主要字段：

```text
condition
nearest_condition
require_like
revert_payload
control_path
merged_conditions
discarded_before_revert
elided_by_native_precompile
```

### 6.2 RawRevertBytes

来源：

```text
revert(add(32, bytesObj), mload(bytesObj))
```

判断规则：

```text
payload_ptr 被 ExpressionRole 标注为 revert_payload_ptr。
对象必须被 TypeEnv 判断为 bytes memory。
payload_size 等于 bytesObj.length，或来自 mload(bytesObj)。
```

记录：

```text
source_object
payload = bytesObj[0:bytesObj.length]
guard
```

实际例子：

```solidity
function _revert(bytes memory returndata) private pure {
    if (returndata.length > 0) {
        assembly {
            let returndata_size := mload(returndata)
            revert(add(32, returndata), returndata_size)
        }
    }
}
```

底层 effect 形态：

```json
[
  {
    "kind": "MemoryRead",
    "attrs": {
      "read_from": "returndata",
      "value": "returndata_size"
    }
  },
  {
    "kind": "Revert",
    "attrs": {
      "payload_ptr": "add(32, returndata)",
      "payload_size": "returndata_size"
    }
  }
]
```

Expression Role 先把指针识别为 bytes 数据区：

```json
{
  "role": "revert_payload_ptr",
  "text": "add(32, returndata)",
  "normalized": "returndata.data",
  "attrs": {
    "object": "returndata"
  }
}
```

随后 `raw_revert_bytes()` 检查：

```text
1. 当前 effect 必须是 Revert；
2. Revert 的 stmt_refs 上存在 role=revert_payload_ptr；
3. role.attrs.object 是 bytes memory；
4. payload_size 等于 object.length，或 payload_size 来自 mload(object) 的 MemoryRead value。
```

生成的高级 overlay：

```json
{
  "kind": "RawRevertBytes",
  "attrs": {
    "source_object": "returndata",
    "payload": "returndata[0:returndata.length]",
    "guard": "returndata.length > 0"
  }
}
```

语义说明：

```text
这表示“原样转发 bytes memory 中保存的 revert payload”。
它不是 revert(string(returndata))，因为后者会重新 ABI 编码 Error(string)，语义不同。
因此 solidity-like 视图不会把它强行改写成普通 Solidity revert(string)。
```

### 6.3 CustomErrorRevert(暂时保留)

来源：

```text
Solidity revert CustomError()
Yul revert 的 payload_memory_partial 中可解析出 error selector
```

判断规则：

```text
selector_registry 中按 selector 匹配 kind=error 的签名。
```

当前代码有两条路径生成 `CustomErrorRevert`。

第一条路径：Solidity 原生 revert。

```solidity
error FailedInnerCall();

function f() internal pure {
    revert FailedInnerCall();
}
```

EffectLifter 对 Solidity 语句生成：

```json
{
  "kind": "Revert",
  "attrs": {
    "payload": "FailedInnerCall();",
    "language": "solidity"
  }
}
```

`solidity_custom_errors()` 只要看到 `Revert.attrs.payload` 是非空字符串，就生成：

```json
{
  "kind": "CustomErrorRevert",
  "attrs": {
    "error": "FailedInnerCall();"
  }
}
```

第二条路径：Yul 中手工写 selector 后 revert。

```yul
mstore(0x00, 0xd125259c) // LinkMirrorContractFailed()
revert(0x1c, 0x04)
```

这里 `revert(0x1c, 0x04)` 只返回从 `0x1c` 开始的 4 字节。EffectLifter 会尝试构造 `payload_memory_partial`，其中记录 selector 来源。随后：

```text
custom_error_selector_overlays()
  -> selector_info_from_partial(payload_memory_partial, preferred_kind="error")
  -> selector_registry 匹配 error selector
```

生成形态：

```json
{
  "kind": "CustomErrorRevert",
  "attrs": {
    "selector": "0xd125259c",
    "selector_source": "low_bytes(0xd125259c, 4)",
    "error": "LinkMirrorContractFailed()",
    "revert_like": "revert LinkMirrorContractFailed();",
    "selector_match": {
      "match_status": "matched",
      "preferred_kind": "error"
    }
  }
}
```

如果 selector 没有匹配到源码中的 error 定义，则不会生成这个 selector 型 `CustomErrorRevert`，底层 `Revert` 仍保留在 effects 中。

### 6.4 MappingSlot / MappingRead / MappingWrite

来源：

```text
keccak256(memory[key, slot], 64)
sload(hash)
sstore(hash, value)
```

判断规则：

```text
MemoryHash 先作为候选保存。
只有 sload/sstore 消费该 hash 的 SSA slot version 时才激活 MappingSlot。
MemoryHash 的输入 words 必须能恢复为 key + state variable slot。
state variable slot 来自 TypeEnv / storage layout。
```

支持 nested mapping：

```text
如果 base 本身是已激活 mapping slot，则生成 nested_mapping_slot。
```

多版本 slot：

```text
如果同一 storage effect 有多个 slot_versions，则生成 PathConditionedStorageRead / PathConditionedStorageWrite。
每个 candidate 单独记录 resolved/unresolved、access、solidity_like。
```

### 6.5 StateVariableRead / StateVariableWrite

来源：

```text
sload(slot)
sstore(slot, value)
```

判断规则：

```text
如果 slot 可以通过 TypeEnv.state_var_by_slot 映射到状态变量，则恢复为状态变量读写。
否则保留为 storage[slot]，并记录 unresolved_reason=unknown_storage_slot。
```

### 6.6 EventEmit

来源：

```text
EventLog
```

判断规则：

```text
parse_events_from_source 解析源码 event 定义。
topic0 必须与事件完整 32 字节 topic0 精确匹配。
anonymous event 按 topics 数量匹配。
indexed 参数来自 topics，非 indexed 参数来自 data_memory words。
```

未匹配时：

```text
event = unknownEvent
notes 包含 unknown_event_topic0
如果 topic0 前缀接近已知事件但完整值不一致，记录 topic0_near_misses。
```

### 6.7 LowLevelCall / StaticCallOverlay / DelegateCallOverlay / PrecompileCall

来源：

```text
Call
StaticCall
DelegateCall
CallCode
```

判断规则：

```text
根据 effect.kind 映射到低层调用 overlay。
target 若是整数地址，转为 address(0x...)。
如果 target 是 Ethereum precompile 地址，则生成 PrecompileCall。
input_memory_partial 可解析 selector 时，用 selector_registry 匹配函数签名。
```

Precompile 处理：

```text
PRECOMPILES 表识别固定地址。
native_precompile_call 可将部分 precompile 调用恢复为 sha256/ripemd160/ecrecover 等 Solidity-like 表达。
如果输入受路径条件影响，则保留 path_conditioned_input，不强行 native lift。
```

### 6.8 PrecompileOutputRead(可能存在冗余，暂且保留)

来源：

```text
PrecompileCall 后续 mload(output_ptr)
```

判断规则：

```text
读取地址必须等于 precompile output_ptr。
读取节点必须发生在 call 后。
中间不能有同地址 memory rewrite。
```

实际例子：

```yul
let ptr := mload(0x40)
mstore(ptr, shl(96, caller()))
let ok := staticcall(gas(), 2, ptr, 20, ptr, 32)
let h := mload(ptr)
```

其中 target `2` 是 Ethereum precompile 地址，当前 `PRECOMPILES` 表会把它识别为 `sha256`。底层 effect 大致是：

```json
[
  {
    "kind": "StaticCall",
    "attrs": {
      "target": "2",
      "input_ptr": "ptr",
      "input_size": "20",
      "output_ptr": "ptr",
      "output_size": "32",
      "input_memory": {
        "words": [
          {
            "value": "shl(96, caller())"
          }
        ]
      }
    }
  },
  {
    "kind": "MemoryRead",
    "attrs": {
      "read_from": "ptr",
      "value": "h"
    }
  }
]
```

先生成 `PrecompileCall`：

```json
{
  "kind": "PrecompileCall",
  "attrs": {
    "precompile": "sha256",
    "input_words": ["(msg.sender << 96)"],
    "native_precompile": {
      "solidity_like": "bytes32 sha256_result_N = sha256(abi.encodePacked(bytes20(msg.sender)));",
      "output_word_expression": "uint256(sha256_result_N)"
    },
    "solidity_like": "bytes32 sha256_result_N = sha256(abi.encodePacked(bytes20(msg.sender)));"
  }
}
```

然后 `precompile_output_overlays()` 再查找后续 `MemoryRead`：

```text
1. MemoryRead.read_from 与 PrecompileCall.output_ptr 相同；
2. MemoryRead 的 cfg_node_id 在 call 的 cfg_node_id 之后；
3. call 与 read 之间没有同 output_ptr 的 MemoryWrite；
4. PrecompileCall.native_precompile.output_word_expression 存在。
```

匹配后生成：

```json
{
  "kind": "PrecompileOutputRead",
  "effects": ["staticcall_effect", "mload_effect"],
  "attrs": {
    "source_precompile_overlay": "ov_precompile",
    "target": "h",
    "value": "uint256(sha256_result_N)",
    "solidity_like": "h = uint256(sha256_result_N);"
  }
}
```

语义说明：

```text
PrecompileCall 表示“调用了固定地址预编译合约”。
PrecompileOutputRead 表示“后续 mload(output_ptr) 读取的是该 precompile 的返回值”。
二者共同把 staticcall + mload 的组合恢复为一个更接近 Solidity 的赋值。
```

### 6.9 AbiCallDataConstruction / AbiEncodedLowLevelCall

来源：

```text
LowLevelCall / StaticCallOverlay / DelegateCallOverlay
```

判断规则：

```text
从 call input_ptr 解析 base 和 start_offset。
向前收集同 base 的 MemoryWrite。
如果某个 32 字节写入覆盖 input_ptr 开始的 4 字节，则提取 selector。
selector 使用 selector_registry 匹配函数签名。
后续 ABI head word 按 relative_offset >= 4 且 32 字节对齐识别。
input_size 表达式可识别 add(0x44, shl(5, mload(x))) 等动态数组模式。
如果参数值来自 StructFieldRead，则补充 value_semantic，例如 p.logs。
```

记录字段：

```text
input_ptr
input_size
input_size_expression
base
start_offset
selector
selector_source
selector_write_effect
selector_match
signature
head_words
arguments
raw_memory_writes
construction_model = call_sink_symbolic_base_backward_memoryssa
complete
```

`AbiEncodedLowLevelCall` 在此基础上生成：

```text
solidity_like = yulCall/yulStaticcall/yulDelegatecall(... abi.encodeWithSelector(...) ...)
```

### 6.10 MemoryRegionAllocate / MemoryRegionWrite

来源：

```text
mload(0x40)
mstore(0x40, newFreePointer)
两者之间写入 mload(0x40) 派生内存区域的数据
```

判断规则：

```text
manual_memory_allocations 找最近的 mload(0x40) 与后续 mstore(0x40, value)。
memory_writes_inside_allocation 只收集分配区间内、非 0x40、非返回 struct 接收体字段的内存写。
地址 alias base 必须是 mload(0x40) 或 add(mload(0x40), ...)。
```

与 MemoryRead / MemoryWrite 的关系：

```text
MemoryRegionAllocate / MemoryRegionWrite 不替代 MemoryWrite，也不会删除底层 MemoryWrite。
它们是叠加在 MemoryWrite 之上的高级解释层。
```

也就是说，同一条 Yul：

```yul
mstore(logs, n)
```

可以同时在模型中出现：

```text
Effect: MemoryWrite(address=logs, value=n)
Overlay: MemoryRegionWrite(region_base=mload(0x40), address=logs, value=n)
```

这不是冲突，而是两层语义：

```text
MemoryWrite 表示“某个地址被写入了 n”。
MemoryRegionWrite 表示“这个写入属于一次 free-memory-pointer 手工分配出来的内存区域”。
```

实际例子：

```yul
let logs := add(mload(0x40), 0x40)
mstore(logs, n)
let offset := add(0x20, logs)
mstore(0x40, add(offset, shl(5, n)))
```

底层仍记录：

```json
{
  "kind": "MemoryWrite",
  "attrs": {
    "address": "logs",
    "value": "n"
  }
}
```

同时高级层记录：

```json
{
  "kind": "MemoryRegionAllocate",
  "attrs": {
    "base": "mload(0x40)",
    "new_free_pointer": "(offset + (n << 5))",
    "stored_values": [
      {
        "address": "logs",
        "value": "n"
      }
    ]
  }
}
```

如果这些写入还能匹配返回 struct 字段，则还会进一步出现 `StructInitializationFragment`。因此它和普通内存读写不是互斥关系，而是：

```text
MemoryWrite -> MemoryRegionWrite -> StructInitializationFragment
```

逐层提高语义抽象。

### 6.11 StructInitializationFragment

来源：

```text
函数具名返回值是 memory pointer / memory struct
assembly 中向该返回对象字段写入内存对象指针或值
```

判断规则：

```text
TypeEnv 判断返回变量是 memory pointer return。
TypeEnv 能获得该返回变量的 struct layout。
MemoryWrite 的 alias base 等于返回变量名，offset 能映射到 struct 字段。
```

记录：

```text
target
type
struct_type
fields
allocation
solidity_equivalent = not_exact
reason = manual_memory_layout_or_custom_allocator
solidity_like
```

### 6.12 StructFieldRead / StructFieldWrite / StructMutationFragment

来源：

```text
对 memory struct 参数、返回值或局部变量的字段读写
```

判断规则：

```text
unit.parameters + unit.returns + unit.locals 中变量被 TypeEnv 判断为 memory struct。
MemoryRead/MemoryWrite 的 address alias base 等于 struct 变量名。
offset 能通过 struct layout 映射到字段。
```

分别记录：

```text
StructFieldRead: struct_object, struct_type, field, value, read_from, solidity_like
StructFieldWrite: struct_object, struct_type, field, value, value_normalized, solidity_like
StructMutationFragment: mutations, related_memory_writes, semantic_hint=struct_field_update
```

### 6.13 CursorBasedMemoryWrite

来源：

```text
先从 struct 字段读出一个 cursor，再向 cursor 指向的内存写入数据。
```

判断规则：

```text
StructFieldRead 得到 cursor_var。
后续 MemoryWrite.address 等于该 cursor_var。
则记录该写入与 struct 字段 cursor 的关系。
```

典型语义：

```text
修改 struct 中保存的内存区域，同时可能更新 struct 字段指针。
```

### 6.14 StoragePointerSlotBinding

来源：

```yul
$.slot := 0xa20d...
```

判断规则：

```text
ValueDef 的 target 以 .slot 结尾，且不是数组/调用形式。
```

记录：

```text
pointer
slot
slot_normalized
solidity_equivalent = false
reason = storage_reference_slot_binding_requires_inline_assembly
solidity_like = /* storage pointer binding: $.slot := ... */
```

### 6.15 ExpressionNormalization / EvaluationStep Overlay

来源：

```text
ValueDef
Branch
EvaluationStep effect
```

判断规则：

```text
ValueDef 转为 target = normalized_expr;
Branch 转为 if (condition_final_temp 或 normalized condition)
EvaluationStep 转为 temp = expression_normalized;
```

其中算术、比较、位运算、环境变量替换由 `s_seir_yul_normalize.normalize_expr` 完成，例如：

```text
add -> +
sub -> -
mul -> *
div -> /
mod -> %
lt/gt/eq/iszero -> Solidity 条件表达式
and/or/xor/not/shl/shr -> 位运算或逻辑归一
caller() -> msg.sender
gas() -> gasleft()
```

### 7.3 归一角色：SemanticNormalizer

`SemanticNormalizer` 会基于已经生成的 effect / overlay 补充第二批 role。它的作用是把不同模块的局部结果统一成可查询的表达式角色。

按 effect 生成的 role：

```text

  ptr  -> memory_slice_start
  size -> memory_slice_size

  value     -> memory_read_value

  value -> storage_write_value

  target      -> call_target
  gas         -> call_gas
  input_ptr   -> call_input_ptr
  input_size  -> call_input_size
  output_ptr  -> call_output_ptr
  output_size -> call_output_size

  data_ptr  -> memory_slice_start
  data_size -> memory_slice_size

```

按 overlay 生成的 role：

```text

  args   -> abi_argument

```

### 7.4 角色不是新语义，而是索引层

Expression Role 不会替代 effect 或 overlay。它的作用是把某个表达式在当前语义中的用途标出来，方便后续查询和 LLM 消费。

例如同一个表达式 `o` 可以有多个角色：

```text
在 call 中：o 是 call_output_ptr
在 mload(o) 中：o 是 memory_slice_start
在 ABI calldata 构造中：o 是 calldata base 的一部分
```

这不是冲突，而是同一表达式在不同语义节点中的不同用途。

例子：`DN404._packedLogsSend` 中的调用数据构造。

```yul
let logs := mload(p)
let o := sub(logs, 0x40)
mstore(o, 0x263c69d6)
mstore(add(o, 0x20), 0x20)
let n := add(0x44, shl(5, mload(logs)))
call(gas(), mirror, 0, add(o, 0x1c), n, o, 0x20)
```

相关 role 会把这些表达式分别标为：

```text
p       -> struct_field_ptr / memory_slice_start
logs    -> struct_field_value，语义上可对应 p.logs
add(o, 0x1c) -> call_input_ptr / abi_calldata_ptr
n       -> call_input_size / abi_calldata_size
0x263c69d6 -> abi_selector
logs    -> abi_argument，value_semantic = p.logs
mirror  -> call_target
o       -> call_output_ptr
```

后续 LLM 不需要重新猜 `add(o, 0x1c)` 为什么是 calldata 起点，也不需要从 `mstore(o, selector)` 手动反推 selector；这些用途已经在 role 与 overlay 中记录。

## 10. Solidity-like 导出规则

`s_seir_solidity_like_export.py` 只是 S-SEIR 图的投影视图，不修改源码，也不保证可编译。

输出形式：

```text
优先输出包含 assembly 的完整函数源码。
在函数源码中，将 assembly 块替换为 assembly /* s-seir solidity-like view */。
```

单条 Yul 语句的渲染优先级：

```text
EventEmit
PrecompileOutputRead
PrecompileCall
RequireOverlay
CustomErrorRevert
MappingWrite / MappingRead
StateVariableWrite / StateVariableRead
PathConditionedStorageWrite / PathConditionedStorageRead
StoragePointerSlotBinding
StructFieldRead
MappingSlot
ExpressionNormalization
MemoryWrite
raw Yul fallback
```

条件保留规则：

```text
solidity-like 会从 effect/overlay 的 path_states 中恢复语句所在 condition。
相邻且文本完全相同的 if(condition) 块会做展示层合并。
循环会根据 control 中的 loop-condition / loop-post / loop-body 信息尽量恢复为 for/while 结构。
```

## 11. 当前模型边界

当前实现已经能统一记录：

```text
基础 Yul 表达式归一
MemorySSA / lazy memory query
storage slot / mapping / state variable 读写
condition-revert require
event log
low-level call / precompile / ABI calldata 构造
局部 memory allocation
memory struct 初始化片段
memory struct 字段读写与 cursor 写入
function-level Solidity/Yul CFG 融合
solidity-like 审计视图
```

当前仍应视为语义模型和审计视图，而不是完整 Solidity 反编译器：

```text
部分 Yul 语义没有无损 Solidity 等价物，例如 storage pointer .slot 绑定、手动 memory layout、原样转发 revert bytes。
复杂 ABI 类型、复杂 alias、复杂循环内存构造仍可能保留为 summary / unknown / unresolved。
security_facts 是辅助摘要，后续 LLM 恢复源码时不必强依赖。
```
