## 工作目标

本阶段目标是处理混淆源码中的 Solidity inline assembly，将 assembly 块逐步恢复为更接近 Solidity 高级语义的表示。当前方案不直接修改原始 Solidity 源码，也不动态执行合约，而是先定位并提取每个 assembly 块，再在提取结果上进行语义恢复。

当前完成的工作中都是采用了静态分析的方式。

当前已完成的恢复范围包括：

- Assembly 所属上下文定位。
- Memory 操作恢复。
- Storage slot 计算恢复。
- 状态读取与状态写入恢复。
- 条件分支中的 `revert(0, 0)` 提取。
- 事件 `log0`-`log4` 提取与 `emit` 恢复。

### 2. Memory 操作恢复

内联汇编中大量使用 `mload` 和 `mstore` 操作 memory。它们通常用于构造 `keccak256` 输入、事件数据、外部调用输入或返回缓冲区。

示例：

```Solidity
mstore(p, _from)
mstore(add(p, 32), 0)
let slot := keccak256(p, 64)
```

可恢复为：

```Plain
mem[p] = _from
mem[p+32] = 0
slot = keccak256(_from, 0)
```

上述示例就是此类内联汇编代码中计算 slot 地址常见的方法。

作用：将每个 assembly 块解析为基础语义 IR，并完成 memory 操作的初步恢复。

核心思想：

- 每个 assembly 块维护独立的 `MemoryTracker`。
- `MemoryTracker` 类似一个静态虚拟内存区，记录 `mstore`、`calldatacopy`、`codecopy`、`returndatacopy` 等对 memory 的写入。
- 当遇到 `mload`、`keccak256(ptr, size)`、`logN(ptr, size, ...)` 等这些会用到 memory 中的数据的操作时，则 backward tracing 追踪这些操作的参数来源，从当前 `MemoryTracker` 中读取对应 memory 区间。
- 同时，在测试的过程中，也发现了一些内联汇编代码在计算多个 slot 时会对同一个变量进行反复赋值。所以这里对 Yul 局部变量引入 assembly-local SSA 版本，用于区分同名变量在不同赋值点的含义，降低 backward tracing 误匹配。

当前可恢复内容：

- `mstore` -> `memory[base + offset] = value`。
- `mload` -> `target = memory[ptr]`。
- `keccak256` -> 根据 memory 内容展示 hash 输入。
- `logN` -> 记录 topics 与当时 data 区域的 memory 来源。
- `revert`、`call/staticcall`、条件、循环等基础语句被归类为语义节点。

### 3. Storage Slot 计算恢复

作用：恢复 Storage Slot 计算、状态读取和状态写入。

核心思想：

- 沿用 `MemoryTracker` 思想，因为 Solidity mapping slot 计算本质上依然依赖 memory 中的 key/base slot 排布。
- Slither 的 `variable-order` printer 能够获取状态变量与 slot 的对应关系，这里使用了这一成果，在进行状态变量的修改时，会更改回为对状态变量的修改的形式。
- `keccak256`函数一般在 assembly 中会用来计算变量存储的位置，但是也会有一般的用途，所以这里采用按需激活的方式来处理：只有当该 hash 被 `sload`、`sstore` 等 storage 操作实际消费时，再去 backward tracing 追踪其参数来源，将其判断为 slot 计算；其余情况才被视为普通的`keccak256`操作。
- 继续采用之前的思想，对同名 Yul 变量使用 SSA 版本进行区分，避免后续赋值覆盖前面 slot 语义。

### 4. 条件分支与 Revert 提取

作用：恢复条件分支中的 `revert(0, 0)` 语义，将其转换为 `require(...)` 形式。

核心思想：

- 当前模块只关注 `revert(0, 0)` 的语义恢复，暂不处理恒真、恒假、不透明谓词等复杂化简。
- 当在某个 condition 下遇到 `revert(0, 0)`，优先将最近一层 condition 转换为 `require(!condition)`。
- 只有当上层 condition 块中没有其他有效操作时，才允许合并上层条件。
- 如果上层 condition 中存在其他有效语句，例如 `let tfe9zci := timestamp()`，则不将上层条件直接合并进同一个 `require`。

### 5. 事件提取

作用：恢复 Yul `log0`-`log4` 指令对应的事件语义。

核心思想：

- 先解析 Solidity 源码中的 `event` 定义。
- 对非 anonymous event 计算： `topic0 = keccak256("EventName(type1,type2,...)")`。
- 遇到 `logN(dataOffset, dataSize, topic0, topic1, ...)` 时，先用 `topic0` 匹配已声明 event。
- 匹配成功后：
  - indexed 参数来自 topics。
  - non-indexed 参数来自 `dataOffset/dataSize` 指向的 memory 区间。
  - data 区域通过当前 assembly 块的 `MemoryTracker` 读取。
- 如果 topic0 无法匹配源码中声明的 event，则不强行恢复为标准事件，而是标注为 `UnknownEvent_<topic0前缀>`。

## 四、已形成的阶段性原则

1. 每个 assembly 块独立维护 MemoryTracker，不跨块共享 memory 状态。
2. MemoryTracker 只记录静态语义，不执行合约。
3. `keccak256` 不再一律识别为 slot，只有被 storage 操作消费时才激活为 slot 计算。
4. 对 Yul 局部变量引入 SSA，降低同名变量复用导致的错误回溯。
5. `revert(0, 0)` 的恢复遵守最近 condition 优先原则，不做过度合并。
6. Event 恢复必须先匹配 topic0；无法匹配时标注 UnknownEvent，而不是误恢复为标准事件。
7. log 的 data 参数必须按 log 发生时的 memory 状态读取，不能用后续 `mstore` 补写历史。

### Opaque Predicate 与噪声识别

混淆合约中常插入恒真、恒假或无实际语义的条件，以干扰分析。

这类条件通常可以标注为：

- opaque predicate
- 混淆噪声
- 恒真条件
- 恒假条件

但需要注意：

只有在确认该条件不影响关键状态写入、事件触发、外部调用或 revert 行为时，才能将其降级为噪声。

如果 opaque predicate 控制了 `sstore`、`log`、`call` 或 `revert`，仍然需要保留其控制依赖。
