# 语义模型完善

## 1. 当前结论

当前 S-SEIR / SemanticFact 已经形成可用的高层语义事实层，但还没有完全达到后续解混淆、逻辑漏洞模式匹配所需的“原子化状态转移语义模型”。

更准确地说：

```text
当前模型 = 高层行为事实层
目标模型 = 原子操作 + 路径条件 + 执行顺序 + 状态转移链
```

当前工作不需要推倒重来，后续更适合在现有 `semantic_facts.json`、`sseir.json`、CFG、MemorySSA/SinkResolver 结果之上，再收敛出一层新的原子状态转移 IR。

## 2. 对当前要求的满足情况

### 2.1 Solidity / Yul 同格式记录

当前已经部分满足。

Solidity 和 Yul 最终都会被投影为统一的 `SemanticFact` 结构：

```json
{
  "kind": "StateWrite",
  "source_lang": "solidity/yul",
  "function": "...",
  "condition": "...",
  "reads": [],
  "writes": [],
  "semantic": {}
}
```

Solidity 状态写示例：

```json
{
  "kind": "StateWrite",
  "source_lang": "solidity",
  "lvalue": "allowance[from][msg.sender]",
  "rvalue": "(current - value)",
  "semantic": {
    "operation": "state_write",
    "access": "allowance[from][msg.sender]",
    "state_variable": "allowance"
  }
}
```

Yul 状态写示例：

```json
{
  "kind": "StateWrite",
  "source_lang": "yul",
  "lvalue": "balanceOf[from]",
  "rvalue": "(fromBalance - value)",
  "semantic": {
    "operation": "state_write",
    "access": "balanceOf[from]",
    "state_variable": "balanceOf",
    "slot": "fromSlot"
  }
}
```

不足：

```text
1. 输出中仍保留 solidity_facts / yul_facts 两个分组。
2. Solidity 与 Yul 的 fact 类型分布不同，Yul 中仍有较多 ValueCompute，Solidity 默认不输出低层 ValueCompute。
3. 若要完全来源无关，后续应以 facts 作为唯一主输出，弱化 source_lang 分组。
```

### 2.2 状态变量在什么条件下、按什么顺序被修改

当前只部分满足。

状态写本身已经能够记录：

```json
{
  "kind": "StateWrite",
  "condition": "!(lt(fromBalance, value))",
  "writes": ["balanceOf[from]"],
  "semantic": {
    "operation": "state_write",
    "access": "balanceOf[from]"
  }
}
```

这对于 Yul 中的 `sstore` 恢复已经比较有效。

不足：

```text
1. 条件并不总是完整传播到后续状态写。
   例如 Solidity 中 require(current >= value) 后的状态写，有时没有把该 require 条件合并进 StateWrite.condition。

2. fact_id 不能严格代表函数内真实执行顺序。
   当前实现中最终 facts 是 solidity_facts + yul_facts 后重新编号。
   因此 fact_id 更多是输出顺序，不是统一 CFG 执行顺序。

3. 后续需要显式加入 op_index / cfg_order / path_id / depends_on 等字段，
   或者生成独立的 state_transition_trace。
```

### 2.3 原子化操作

当前不满足严格意义上的全量原子化。

Yul 部分已有较强的原子化迹象，例如：

```json
{
  "kind": "ValueCompute",
  "lvalue": "__sseir_eval_asm_s_5_1",
  "rvalue": "lt(fromBalance, value)"
}
```

但最终状态写仍可能是复合表达式：

```json
{
  "kind": "StateWrite",
  "lvalue": "balanceOf[to]",
  "rvalue": "(balanceOf[to] + value)"
}
```

Solidity 部分也存在复合表达式：

```json
{
  "kind": "StateWrite",
  "lvalue": "maxOwnerMint",
  "rvalue": "(initialSupply * 2)"
}
```

以及：

```json
{
  "kind": "StateWrite",
  "lvalue": "deploymentSalt",
  "rvalue": "keccak256(bytes)(abi.encodePacked(block.chainid,address(this),tokenName))"
}
```

这些不是“一条 fact 只包含一个操作”，而是高层语义 fact。

因此当前模型更适合审计视角的高层行为事实，还不是可直接用于模式匹配的 atomic IR。

## 3. 对后续任务的支持能力

当前模型已经支持：

```text
1. 统一记录 Solidity / Yul 的状态读写。
2. 恢复 Yul mapping slot、sload / sstore、event、require / revert。
3. 记录部分路径条件。
4. 将 Solidity 与 Yul 放入同一种 SemanticFact 结构。
5. 对人工 ERC20 样例中的状态变化有较好覆盖。
```

但要支撑后续解混淆和逻辑漏洞发现，还需要补齐：

```text
1. 完整路径条件传播到每个状态写。
2. 函数内真实执行顺序。
3. Solidity 和 Yul 的统一原子化。
4. 每个原子操作的 def-use 依赖链。
5. 内部调用的跨函数状态影响建模。
6. 对复合表达式拆成稳定表达式树或三地址码 IR。
```

## 4. 后续建议方向

建议在现有模型之上新增一层：

```text
AtomicSemanticIR / StateTransitionIR
```

该层输入：

```text
semantic_facts.json
sseir.json
function-level CFG
MemorySSA / SinkResolver
Slither typed def-use
```

该层输出应重点围绕：

```text
1. 原子操作序列
2. 路径条件
3. 状态变量读写
4. 操作顺序
5. def-use 依赖
6. 可用于模式匹配的状态转移事实
```

最终目标是让逻辑漏洞检测可以围绕如下问题展开：

```text
在什么路径条件下，
按照什么顺序，
读取了哪些状态，
计算了哪些中间值，
最终写入了哪些状态变量。
```
