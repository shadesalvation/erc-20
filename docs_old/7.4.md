## 工作目标

本阶段目标是在 6.25 阶段已经形成的 CFG、MemorySSA、Storage/Event/Call/Revert 等模块基础上，进一步将这些分散的恢复结果统一到一个函数级语义模型中，即 S-SEIR。

6.25 阶段的 pipeline 已经可以把 inline assembly 恢复成 Solidity-like semantic view，但这种结果仍然更接近“文本化恢复结果”。后续如果直接把这类文本交给 LLM，会遇到两个问题：

- 有些 Yul 语义本身无法无损恢复为 Solidity 高级语句，例如 raw revert bytes、低级 call、部分 memory 操作等。
- 原模块之间各自有自己的中间表示，缺少统一的 effect、overlay、projection policy，后续 LLM 需要理解多个模块的输出格式。

因此本阶段的重点从“继续把 Yul 改写成 Solidity-like 文本”调整为“建立统一语义模型”。

当前 S-SEIR 的目标是：

```Plain
Solidity / Yul Source Statements
  -> Function-level Control Graph
  -> Expression Roles
  -> Low-level Effects
  -> Semantic Overlays
  -> Projection Policies
  -> Security Facts / Analysis Facts
```

其中确定性静态分析仍然负责所有关键语义判断，LLM 只应在后续源码重建阶段消费这些结构化事实，而不直接参与语义推断。

## 二、模块说明

### 1. S-SEIR 数据模型

作用：定义统一的函数级语义容器，用于承载 Solidity 语句、Yul 语句、控制流、表达式角色、副作用、高级语义解释和投影策略。

核心结构：

```Plain
FunctionSSEIR:
  source_statements
  control
  expr_roles
  effects
  semantic_overlays
  projection_policies
  security_facts
  analysis_facts
```

做这一步的目的：

原模块中 MemorySSA、Storage 恢复、Event 恢复、External Call 恢复等都能独立完成部分工作，但它们的输出格式不统一。S-SEIR 将这些结果统一为两层：

- `EffectNode`：记录底层确定性副作用，例如 `MemoryWrite / StorageRead / StaticCall / EventLog / Revert`。
- `SemanticOverlay`：记录对底层 effect 的高级解释，例如 `MappingRead / MappingWrite / EventEmit / PrecompileCall / RequireOverlay`。

示例：

```Plain
Effect:
  StorageWrite(slot=Jfwv, value=sub(zfPf, _amount))

Overlay:
  MappingWrite(access=wZHA[_owner][_spender], value=zfPf - _amount)
```

当前原则：

- 正式 IR 中不保存 `confidence` 字段。
- 不构建复杂 provenance graph，只保留 `stmt_refs`。
- 不把所有内容都强行投影为 Solidity 语句，无法无损表达的语义通过 `ProjectionPolicy` 标注。

### 2. Source Statement Table

作用：统一记录 Solidity 与 Yul 原始语句，并为后续 effect、overlay、policy 提供证据引用。

核心做法：

- Solidity 语句分配 `sol_s_x`。
- Yul / inline assembly 语句分配 `asm_s_x`。
- 每条语句记录：
  - `stmt_id`
  - `lang`
  - `text`
  - `src`
  - `function_id`
  - `block_id`

示例输出：

```Plain
SourceStatements:
  asm_s_5 [yul] let bbwz := mload(0x40)
  asm_s_9 [yul] mstore(bbwz, _from)
  asm_s_15 [yul] if iszero(staticcall(gas(), 2, bbwz, 20, bbwz, 32))
```

作用：后续任意语义节点都只需要引用 `stmt_refs`，不需要在每个节点里重复保存完整源码。

### 3. Function-level CFG 融合

作用：将 Solidity 函数级 CFG 与 assembly 内部 Yul CFG 融合，形成 S-SEIR 的统一 control layer。

做这一步的目的：

前面的 CFG 主要服务于单个 assembly 块，而当前处理单元需要提升到函数级。原因是同一函数中可能存在多个 assembly 块，且 Solidity 局部变量、return 变量、loop、if 等都会影响 Yul 语义解释。

当前采用的方案：

```Plain
Solidity 函数级 CFG：复用 Slither function CFG
Yul / inline assembly 内部 CFG：复用原 assembly_ast_cfg
融合方式：用本地 Yul CFG 子图替换 Slither 中 assembly anchor 节点
```

核心做法：

- 使用 Slither 获取函数级 Solidity CFG。
- 使用 solc AST 提取每个 InlineAssembly 对应的 Yul AST。
- 使用原 `assembly_ast_cfg` 为 Yul AST 构建局部 CFG。
- 对 Slither 中位于 assembly 源码范围内的节点，只作为 anchor 使用。
- 将 Slither 前驱边连接到 Yul CFG entry。
- 将 Yul CFG exit 连接到 Slither 后继节点。
- 对 Solidity loop 包裹 assembly 的情况，在 assembly block 上附加 `function_loop_context`。

当前样例输出中 control layer 已包含：

```Plain
note: function_level_cfg_from_slither
note: assembly_subgraph_embedded_from_assembly_ast_cfg
note: slither_assembly_nodes_replaced_by_local_yul_cfg
note: assembly_edge_policy=slither_predecessors_to_yul_entry_and_yul_exit_to_slither_successors
```

这说明当前 S-SEIR 已经不是单纯的 assembly block 输出，而是以函数为容器，将 Solidity CFG 与 Yul CFG 放入同一个控制流视图中。

### 4. S-SEIR MemorySSA 查询层

作用：将原来的 MemoryTracker / MemorySSA 思路迁移到 S-SEIR 中，作为后续 storage、event、call、return、revert 等语义终点的统一 memory 查询基础。

做这一步的目的：

前面的模块已经证明，Yul 语义恢复的关键不是立即执行 memory，而是记录 memory write，并在语义终点处按需读取。例如：

- `keccak256(ptr, len)` 需要读取 slot 构造材料。
- `logN(ptr, len, ...)` 需要读取 event data。
- `call/staticcall` 需要读取 input memory。
- `revert/return` 需要读取 payload memory。

当前 S-SEIR 中继续保留这些核心思想：

- 不动态执行合约。
- 不在前向阶段过度展开所有路径。
- 只在语义终点读取 memory 时进行 backward tracking / lazy resolve。
- 保留 PathState、linear alias、branch candidates、loop phi、range summary、MemoryTop 等事实。

当前样例输出中已经记录：

```Plain
MemorySSAQueryLayer:
  scope = s_seir_function_memoryssa_view
  features = path_states, linear_aliases, branch_candidates,
             loop_phi_facts, range_summary_facts, memory_top_facts
```

### 5. 线性地址 alias 增强

作用：增强 MemorySSA 对 memory 地址的识别能力，避免只按原始表达式匹配导致漏追踪。

做这一步的目的：

Yul 中常出现这种形式：

```Solidity
let base1 := add(base0, 4)
mstore(add(base1, 4), v)
```

如果只记录原始地址表达式 `add(base1, 4)`，后续以 `base0 + 8` 读取时可能无法匹配。因此当前只对线性地址进行 alias 记录：

```Plain
addr = base1 + 4
addr = base0 + 8
```

当前原则：

- 只保留线性 alias。
- 不对复杂非线性表达式强行推导。
- 无法确认 alias 时保守保留原始表达式或退化为 unknown / MemoryTop。

这部分继续沿用前面 MemorySSA 的思想，只是把结果纳入 S-SEIR 的 memory query attrs 中，让 effect 和 overlay 可以直接引用。

### 6. Loop-aware Lazy MemorySSA 接入 S-SEIR

作用：将 6.25 阶段形成的 loop-aware lazy 思想纳入 S-SEIR 的 function-level 分析链路。

核心规则继续保留：

```Plain
前向阶段不无限展开 loop
遇到 loop memory write 时建立 loop summary
语义终点读取相关 memory 时再 lazy materialize
```

当前接入方式：

- S-SEIR control layer 负责识别函数级 loop 上下文。
- Yul loop 继续由原 Yul CFG / MemorySSA 识别。
- MemorySSA facts 中保留：
  - `LoopMemoryRecord`
  - `MemoryPhi`
  - `MemoryRangeSummary`
  - `MemoryTop`
- 语义终点的 memory query 中记录 loop alignment 信息。

示例：

```Plain
loop_alignment = function_level_solidity_loop_context_plus_yul_loop_memoryssa
```

这表示当前 S-SEIR 会统一考虑 Solidity loop 包裹 assembly 与 Yul 内部 loop 两类情况，但仍保持“不盲目展开循环”的原则。

### 7. Effect Lifter

作用：将 Solidity / Yul 的底层语义提升为统一的 `EffectNode`。

当前支持的主要 effect 包括：

- `MemoryRead`
- `MemoryWrite`
- `MemoryHash`
- `StorageRead`
- `StorageWrite`
- `EventLog`
- `Call / StaticCall / DelegateCall / CallCode`
- `Require / Revert / Return`
- `ValueDef`

做这一步的目的：

Effect layer 只记录事实，不做过度解释。例如 `sload(Jfwv)` 只先记录为：

```Plain
StorageRead(slot=Jfwv)
```

是否能解释为：

```Plain
wZHA[_owner][_spender]
```

则由后续 overlay builder 根据 MemorySSA、storage layout、SSA version、hash input 等事实判断。

### 8. Semantic Overlay Builder

作用：将底层 effect 解释为更接近 Solidity 语义的 overlay。

当前主要 overlay 包括：

- `RequireOverlay`
- `MappingSlot`
- `MappingRead`
- `MappingWrite`
- `StateVariableRead`
- `StateVariableWrite`
- `EventEmit`
- `LowLevelCall`
- `PrecompileCall`
- `PrecompileOutputRead`
- `RawRevertBytes` 基础框架

做这一步的目的：

旧 pipeline 的“Solidity-like 文本”本质上应该来自 overlay，而不是直接来自某个模块的文本替换。这样后续 LLM 不需要理解 `mstore / keccak256 / sload` 的完整过程，只需要消费已经结构化后的语义事实。

示例：

```Plain
MappingRead:
  access = UbLX[_from]
  target = qVPd

MappingWrite:
  access = UbLX[_from]
  value = qVPd - _amount
```

### 9. ProjectionPolicy

作用：判断某个 overlay 是否可以被无损投影为 Solidity 高级语句。

当前区分的输出类型包括：

- `solidity_statement`
- `solidity_expression`
- `low_level_call_statement`
- `assembly_preserved`
- `semantic_comment`
- `unresolved`

做这一步的目的：

有些 overlay 虽然语义明确，但 Solidity 高级语言没有无损等价写法。例如 raw revert bytes 不能简单写成 `revert(string(returndata))`，因为后者会重新 ABI 编码。因此这类情况应通过 ProjectionPolicy 明确标注为 `assembly_preserved`，而不是让后续 LLM 自行猜测。

### 10. Security Facts

作用：从 effect 和 overlay 中抽取安全行为事实，用于后续安全行为切片或漏洞分析。

当前样例中已经能看到：

```Plain
ExternalCall
ExternalCallBeforeStateUpdate
EventEmission
```

例如 `_transfer` 中 SHA256 precompile 调用发生在状态更新前，因此记录为：

```Plain
ExternalCallBeforeStateUpdate(call=eff_42, state_update=eff_56)
ExternalCallBeforeStateUpdate(call=eff_42, state_update=eff_61)
```

这类事实不是源码恢复本身，但会成为后续安全分析和 LLM 解释的重要结构化输入。

### 11. 脚本结构整理

作用：将旧模块与 S-SEIR 新模块分目录管理。

当前结构：

```Plain
scripts/legacy_yul/
  原 assembly 恢复模块

scripts/s_seir/
  S-SEIR 统一语义模型模块
```

整理后的意义：

- 原模块作为历史实现与算法参考保留。
- 后续新增和修改应优先发生在 `scripts/s_seir/`。
- S-SEIR 不应长期只是 adapter 搬运旧结果，而应逐步复现并统一旧模块中的核心算法。

当前仍保留了部分 scripts 根目录文件，主要是兼容和历史入口；后续正式开发应以 `scripts/s_seir/` 为主。

## 三、当前处理结果

当前使用样例：

```Plain
TOKENS/0x0068e979c72bbb31373ea8cb47eaefb44978566e/Token.sol
```

输出文件：

```Plain
outputs/0x0068e979c72bbb31373ea8cb47eaefb44978566e.sseir_check.json
outputs/0x0068e979c72bbb31373ea8cb47eaefb44978566e.sseir_check.txt
```

### 1. 函数级 S-SEIR 输出已经形成

以 `_transfer(address,address,uint256)` 为例，当前输出包含：

```Plain
Function Token._transfer(address, address, uint256)
  SourceStatements
  Control
  ExpressionRoles
  Effects
  SemanticOverlays
  ProjectionPolicies
  SecurityFacts
  AnalysisFacts
```

这说明当前输出已经不只是 assembly 块恢复结果，而是函数级语义模型。

### 2. Storage 语义恢复结果

`_transfer` 中已经可以恢复出余额 mapping 的读写：

```Plain
MappingRead:
  qVPd = UbLX[_from]

MappingWrite:
  UbLX[_from] = qVPd - _amount

MappingRead:
  bXFg = UbLX[_to]

MappingWrite:
  UbLX[_to] = bXFg + _amount
```

对应样例输出片段：

```Plain
ov_13 MappingRead  access=UbLX[_from]
ov_15 MappingWrite access=UbLX[_from]
ov_16 MappingRead  access=UbLX[_to]
ov_17 MappingWrite access=UbLX[_to]
```

这说明 S-SEIR 中的 storage overlay 已经能够消费 MemorySSA 中的 keccak 输入、storage layout 和 SSA 信息。

### 3. Precompile 调用恢复结果

`_transfer` 中存在：

```Solidity
staticcall(gas(), 2, bbwz, 20, bbwz, 32)
```

地址 `0x02` 是 SHA256 precompile。当前 S-SEIR 可以从 memory input 中解析：

```Plain
input_words = [(msg.sender << 96)]
```

并恢复出高级语义：

```Plain
bytes32 sha256_result_19 = sha256(abi.encodePacked(bytes20(msg.sender)));
YvIh = uint256(sha256_result_19);
```

同时保留底层调用事实：

```Plain
Effect: StaticCall
Overlay: PrecompileCall
Overlay: PrecompileOutputRead
SecurityFact: ExternalCall
```

这比 6.25 阶段单纯输出 Solidity-like 文本更结构化，因为同一语义同时有底层 effect、高级 overlay 和安全事实。

### 4. Revert / Require 恢复结果

当前 `revert(0,0)` 继续恢复为 `RequireOverlay`，并保留最近 condition 优先原则。

示例：

```Plain
RequireOverlay:
  require(_from != address(0));

RequireOverlay:
  require((tfe9zci != (tfe9zci * 1)));
```

第二个例子说明当前仍然遵守之前修正过的规则：如果 revert 上层 condition 中存在其他有效操作，则不把所有上层 condition 粗暴合并进同一个 require。

### 5. Event 恢复结果

`approve` 函数中当前输出：

```Plain
EventEmit:
  event = unknownEvent
  topic0 = 0x8c5be1e5ebec7d5bd14f714f4f5ec7c46ab3db174da78c3f62f10b71e9aeeaa0
  emit_like = emit unknownEvent(msg.sender, _spender, _spender);
```

原因分析：

- 源码中声明的 `Approval(address,address,uint256)` topic0 与该 log 的 topic0 不一致。
- 按 EVM 事件规则，topic0 不匹配时不能强行恢复为 `Approval`。
- 因此当前标注为 `unknownEvent` 是正确的保守结果。

### 6. SSA 版本修复结果

本阶段还修复了 S-SEIR 中一个重要问题：同名 Yul 变量的不同 SSA 版本在 overlay 匹配时被压扁。

问题表现：

```Plain
Jfwv := keccak256(...)
...
Jfwv := keccak256(...)
```

如果 overlay builder 只按变量名 `Jfwv` 建索引，会把不同版本的 `Jfwv` 混在一起，导致 storage read/write 被错误匹配到错误的 mapping slot。

修复方式：

- `MemoryHash` 增加 `value_versions`。
- `StorageRead / StorageWrite` 增加 `slot_versions`。
- `MappingSlot / MappingRead / MappingWrite` 优先按 SSA version 匹配。
- 只有缺失版本信息时才回退到原始变量名。

修复后 `_spendAllowance` 中：

```Plain
CCkU = sload(Jfwv)
```

不会再被错误投影为 `wZHA[_owner][_spender]`，而是保守保留为：

```Plain
StateVariableRead:
  access = storage[Jfwv]
  unresolved_reason = unknown_storage_slot
```

后续真正对应 allowance 的：

```Plain
zfPf = sload(Jfwv)
```

可以恢复为：

```Plain
MappingRead:
  zfPf = wZHA[_owner][_spender]
```

对应的写入也能恢复为：

```Plain
MappingWrite:
  wZHA[_owner][_spender] = zfPf - _amount
```

这说明 SSA 技术本身是必要且有效的，问题出在 S-SEIR 迁移时丢失了 SSA 版本信息。

## 四、当前分析结论

### 1. S-SEIR 已经从 adapter 过渡到原生语义图

当前输出中存在：

```Plain
SSEIRCanonicalization:
  mode = native_s_seir_semantic_graph
  legacy_adapter_used = false
```

这说明当前不再只是搬运旧 pipeline 的文本结果，而是已经在 S-SEIR 中直接形成 source statement、effect、overlay、policy、security fact 等结构化节点。

### 2. 原模块中的关键思想仍然保留

6.18 和 6.25 中形成的核心规则在 S-SEIR 中仍然适用：

- CFG 驱动数据流分析。
- MemorySSA 作为 memory 语义恢复基础。
- `keccak256` 按需激活为 storage slot。
- 语义终点触发 memory query。
- loop 采用 summary + lazy resolve。
- unknown / dynamic alias 不强行恢复。
- event 必须 topic0 精确匹配。
- external call 未知目标不强行 ABI 恢复。
- precompile 可以提升为 Solidity 内置函数。
- `revert(0,0)` 遵守最近 condition 优先原则。

### 3. 当前结果仍不是最终 Solidity 源码

S-SEIR 的当前输出是语义模型，不是最终源码替换结果。

也就是说，当前可以回答：

```Plain
这个 assembly 块做了哪些 memory 写入？
哪些 storage slot 被读写？
哪些 log 是真实 event？
哪些 call 是 precompile？
哪些 revert 可以投影为 require？
哪些语义不能无损恢复为 Solidity？
```

但还没有完成：

```Plain
根据 S-SEIR 自动生成可编译 Solidity 函数体
替换原始 assembly 块
通过 solc 编译验证
```

### 4. 与真实源码语义对比的阶段性结果

对当前样例进行语义对比时，可以看到：

- `_transfer` 的余额扣减和增加语义基本恢复正确。
- SHA256 precompile 调用能够恢复为 Solidity 内置 `sha256(...)` 语义。
- `approve` 中 storage 写入恢复为 `wZHA[msg.sender][_spender] = _amount`。
- `approve` 中 log 不能恢复为 `Approval`，因为 topic0 不匹配。
- `_spendAllowance` 中 allowance mapping 的后续读写已通过 SSA 修复恢复得更准确。

当前仍需注意：

- 当 `StorageWrite` 携带多个 `slot_versions` 时，虽然已经避免了错误覆盖，但还没有完全做成 path-conditioned 多候选 overlay。
- 部分 require 条件仍保留混淆表达式，需要后续 opaque predicate / condition cleanup。
- Memory、slot、临时 hash 变量还没有进行最终消解。

## 五、已形成的阶段性原则

1. 后续统一以 `/home/ubuntu/erc-20` 小写目录为最新工作目录。
2. S-SEIR 当前阶段只处理 Yul / inline assembly 的确定性语义建模，不做 LLM 源码生成。
3. 原模块可以作为算法参考，但 S-SEIR 应尽量形成自己的统一 effect / overlay / policy 结构。
4. Solidity 函数级 CFG 优先复用 Slither，Yul 内部 CFG 复用原 `assembly_ast_cfg`。
5. MemorySSA 继续服务于 slot、event、call、return、revert 等语义终点，不在 Solidity 普通语句中做过度 memory 建模。
6. 遇到 loop 时，重点是识别 loop 上下文并记录 summary，而不是区分它一定是 Solidity loop 还是 Yul loop。
7. 地址 alias 只处理线性表达式，复杂表达式保守处理。
8. 同名 Yul 变量必须保留 SSA version，overlay 匹配不能只按变量名。
9. Event 恢复必须严格 topic0 匹配，不能因为函数名或参数像 ERC20 事件就强行恢复。
10. ProjectionPolicy 是静态分析结果，不交给 LLM 决定。
11. LLM 后续只消费 S-SEIR 的结构化语义，不作为关键语义判断来源。

## 六、后续还需完成的工作

***这里只是当前阶段遗留问题总结，后续实现时仍可根据测试结果调整。***

### 1. Path-conditioned Storage Overlay

当前 `StorageRead / StorageWrite` 已经保留 `slot_versions`，但当同一 storage write 在不同路径上有多个 slot version 时，还需要进一步拆分为路径条件化 overlay：

```Plain
if condition_a:
  MappingWrite(... slot_version_a ...)
else:
  unresolved / MappingWrite(... slot_version_b ...)
```

否则虽然不会再简单覆盖，但仍可能在输出中选择了一个可解析候选，而没有充分表达多路径语义。

### 2. Memory / Slot 中间表示消解

当前 S-SEIR 能承载 memory facts，但最终源码恢复前仍需：

- 删除只用于 slot 计算的 memory write。
- 删除只用于 ABI/event/call 编码且已经被消费的 memory write。
- 消解 `slot(...)`、临时 keccak 变量。
- 保留无法消解的 memory chain，并通过 ProjectionPolicy 标注原因。

### 3. Revert Payload 与 Error Selector

当前主要恢复 `revert(0,0)` 和 RawRevertBytes 基础框架。

后续需要继续处理：

- `Error(string)`。
- `Panic(uint256)`。
- custom error selector。
- `revert(ptr, size)` 中 ABI 编码参数。
- raw revert bytes 与 Solidity 可表达 revert 的投影区分。

### 4. Branch Materialization 结构化增强

当前 branch materialization 已进入 analysis facts，但还需要进一步成为正式 overlay / effect 的可查询结构。

需要记录：

- condition。
- 受影响 sink。
- 参与复制的 memory definitions。
- 被丢弃分支原因。
- 与 storage/event/call/revert overlay 的引用关系。

### 5. Event / External Call 深化

Event 侧：

- dynamic event data ABI 解码。
- anonymous event 支持。
- UnknownEvent 参数区分 topic/data 来源。

External call 侧：

- 普通 call 的 selector 和 arguments 结构化恢复。
- returndata 后续使用追踪。
- success result 与 require/revert 的关系建模。
- 低级调用保守投影策略继续细化。

### 6. ProjectionPolicy 驱动源码重建

后续要让 ProjectionPolicy 真正决定：

- 哪些 overlay 可以生成 Solidity statement。
- 哪些只能生成 low-level call。
- 哪些必须保留 assembly。
- 哪些只能输出 semantic comment。
- 哪些 unresolved 节点禁止源码替换。

这一步完成后，才能进入最终 Solidity 源码替换和编译验证。

### 7. 测试体系升级

后续测试需要从单模块样例升级为 S-SEIR 端到端样例：

- function-level CFG 融合测试。
- Solidity loop 包裹 assembly 的 MemorySSA 测试。
- 线性 alias 与 storage/event/call 联动测试。
- path-conditioned storage overlay 测试。
- RawRevertBytes / Error selector 测试。
- S-SEIR JSON/TXT 输出稳定性测试。

## 八、总结

6.18 阶段完成的是基础 inline assembly 语义恢复，重点是 Memory、Storage、Revert、Event 等规则能跑通。

6.25 阶段完成的是 CFG 驱动的数据流增强，重点是 Yul CFG、Path-sensitive MemorySSA、Loop-aware Lazy MemorySSA、分支物化、External Call 和 Precompile 恢复。

本阶段完成的是将前面这些分散的恢复能力统一到 S-SEIR 函数级语义模型中。当前 S-SEIR 已经能够输出 source statements、function-level control、expression roles、effects、semantic overlays、projection policies、security facts 和 analysis facts，并且已经在样例合约上验证了 mapping 读写、precompile、require、unknown event、SSA version 区分等关键语义。

下一阶段重点不应是盲目增加更多文本替换规则，而应继续完善 S-SEIR 的结构化闭环：path-conditioned overlay、memory/slot cleanup、revert payload、projection policy 和最终源码重建。
