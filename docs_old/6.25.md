## 工作目标

本阶段目标是在前一阶段 Memory、Storage、Revert、Event 等基础恢复模块之上，继续处理更复杂的 inline assembly 控制流和数据流问题。

前一阶段的恢复主要依赖从源码文本中提取 assembly 语句，并在单个 assembly 块内维护一个静态 `MemoryTracker`。这种方式可以处理线性语句和一部分简单条件分支，但当 assembly 中存在复杂 `if`、循环、多路径 memory 写入、外部调用参数构造、precompile 调用等情况时，仅靠线性扫描会出现以下问题：

- 不同分支上的 memory 写入可能影响同一个后续 `keccak256 / sload / log / call`。
- loop 中的 memory 写入可能导致路径枚举爆炸。
- 后续模块在恢复 slot、event、external call 时需要更准确的控制流和 memory reaching definition。
- 部分低级调用其实是 EVM precompile，可以恢复为更接近 Solidity 的高级语义。

因此，本阶段工作的重点从“简单规则恢复”推进到“CFG 图 + MemorySSA + 分支物化 + 模块化 pipeline”。

当前新增和更新的主要范围包括：

- 基于 solc AST 构建 assembly 块内部 CFG 图。
- 构建 path-sensitive MemorySSA，并进一步升级为 Loop-aware Lazy MemorySSA。
- 根据 CFG 和 MemorySSA 处理条件分支中会影响语义终点的 memory 写入。
- 将 CFG / MemorySSA 能力接入后续 storage、event、external call 等恢复模块。
- 补充算术、比较、位运算和部分环境操作的 Solidity 化恢复。
- 增加外部调用提取，并对固定地址 precompile 做高级语义改写。
- 更新总 pipeline，使其能够从 Solidity 源码出发，串联 CFG、MemorySSA、分支处理和各语义恢复模块。

## 二、模块说明

### 1. Assembly AST 与 CFG 图构建

作用：从 solc AST 中提取每个 inline assembly 块对应的 Yul AST，并为每个 assembly 块构建局部 CFG 图。

做这一步的目的：

前面的模块虽然能够定位 assembly 源码文本，但文本级顺序扫描无法准确表达 `if / switch / for / break / continue / leave / revert / return` 等控制流关系。后续 MemorySSA、分支处理和 backward tracing 都需要知道某条语句可能由哪些路径到达，所以需要先把 assembly 块转换为 CFG。

核心做法：

- 使用 solc `--standard-json` 获取 Solidity AST。
- 在 AST 中定位 `InlineAssembly` 节点，并读取其中的 Yul AST。
- 对 Yul AST 中的语句构建 CFG 节点和边。
- 对不同语句类型使用不同的控制流规则：
  - 普通语句：顺序连接。
  - `if`：生成 condition 节点、true 边、false 边和 merge 节点。
  - `switch/case/default`：生成 switch 分发节点和 merge 节点。
  - `for`：生成 pre、loop-condition、body、post、loop-merge 和 loop back 边。
  - `break`：连接到 loop merge。
  - `continue`：连接到 loop post。
  - `leave / return / revert / selfdestruct`：连接到 exit。
- 支持导出 DOT 图，方便人工检查 CFG 是否正确。

示例：

```Solidity
assembly {
    let i := 0
    for { } lt(i, 3) { i := add(i, 1) } {
        if eq(i, 1) {
            mstore(ptr, i)
        }
    }
    let h := keccak256(ptr, 0x20)
}
```

CFG 中会形成类似结构：

```Plain
entry
  -> let i := 0
  -> loop-condition lt(i, 3)
      true  -> if eq(i, 1)
               true  -> mstore(ptr, i)
               false -> if merge
               -> loop-post
               -> loop-condition
      false -> loop-merge
  -> let h := keccak256(ptr, 0x20)
  -> exit
```

当前作用：CFG 图现在是 MemorySSA 和分支处理的基础。后续所有需要判断“某个 memory 写入能否到达某个语义终点”的逻辑，都应以 CFG 为依据，而不是只依赖源码行顺序。

### 2. CFG Path-sensitive MemorySSA

作用：在每个 assembly 块内，根据 CFG 构建路径敏感的 memory SSA 和 value SSA。

做这一步的目的：

内联汇编中大量语义不是直接写在 `sload/sstore/log/call` 参数中，而是先写入 memory，再由后续操作读取。例如 mapping slot、event data、call input 都常通过 `mstore` 构造。当前恢复必须知道在某个语义终点处，某段 memory 的来源是什么。

核心思想：

- 每个 assembly 块独立维护 MemorySSA，不跨 assembly 块共享 memory 状态。
- CFG 中每条可达路径携带一个 `PathState`。
- `PathState` 中保存：
  - 当前路径条件。
  - 当前 memory reaching definitions。
  - 当前 Yul 局部变量 value definitions。
- 遇到 `mstore / mstore8 / calldatacopy / codecopy / returndatacopy / mcopy` 时，生成新的 memory definition。
- 遇到 `let x := ...` 或 `x := ...` 时，生成新的 value definition。
- 后续遇到 `mload / keccak256 / log / return / revert / call` 等语义终点时，可以读取当前路径上的 memory 定义。

示例：

```Solidity
assembly {
    mstore(ptr, _from)
    mstore(add(ptr, 32), 0)
    let loc := keccak256(ptr, 64)
    let bal := sload(loc)
}
```

MemorySSA 中会记录：

```Plain
mem_1 = mstore(ptr, _from)
mem_2 = mstore(add(ptr,32), 0)
loc__ssa1 = keccak256(ptr, 64)
```

当 `keccak256(ptr, 64)` 作为语义终点读取 memory 时，可解析为：

```Plain
keccak256 input:
  ptr + 0  = _from
  ptr + 32 = 0
```

这一步使后续 storage 恢复能够继续得到：

```Solidity
bal = balances[_from];
```

### 3. 条件分支物化处理

作用：当不同分支上的 memory 写入会影响后续语义终点时，将这些差异显式物化出来，避免后续恢复阶段只看到一个模糊的 unknown。

做这一步的目的：

有些混淆代码会在 `if` 中改写 memory，然后在分支外统一执行 `keccak256 / sload / sstore`。如果只线性分析，会无法判断最终 slot 或状态变量访问到底来自哪条分支。

示例：

```Solidity
assembly {
    mstore(ptr, _from)
    mstore(add(ptr, 32), 1)
    if condition {
        mstore(ptr, _to)
        mstore(add(ptr, 32), 0)
    }
    let loc := keccak256(ptr, 64)
    let bal := sload(loc)
}
```

这里 `sload(loc)` 是一个语义终点。它的参数 `loc` 来自 `keccak256(ptr, 64)`，而 `ptr` 指向的 memory 在不同分支中不同。

分支处理的目标不是立刻恢复成最终 Solidity，而是先把对语义终点有影响的分支显式展开：

```Plain
mstore(ptr, _from)
mstore(add(ptr, 32), 1)
let loc := keccak256(ptr, 64)
let bal := sload(loc)
if condition {
    mstore(ptr, _to)
    mstore(add(ptr, 32), 0)
    let loc := keccak256(ptr, 64)
    let bal := sload(loc)
}
```

后续 storage 模块再分别恢复为类似：

```Solidity
bal = allowance[_from];
if (condition) {
    bal = balances[_to];
}
```

核心做法：

- 先构建 CFG 和 MemorySSA。
- 找到 `sload / sstore / log / call / return / revert` 等语义终点。
- 对语义终点的参数进行 backward tracing。
- 如果参数来源在不同路径上不同，则提取这些差异来源。
- 将影响语义终点的那部分语句复制到对应 condition 下。
- 如果某条分支包含无法解析的 unknown memory，当前策略是保守丢弃该分支，避免 opaque predicate 干扰后续 solc AST 重新编译。

当前作用：分支物化模块位于 CFG 构建和 MemorySSA 构建之后，其他语义恢复模块之前。它会先产出一份处理过的 assembly 块视图，后续模块再基于新的 assembly 结果重新构建 AST/CFG 并继续恢复。

### 4. Loop-aware Lazy MemorySSA

作用：解决 assembly 中存在循环并且循环体内存在 memory 写入时，普通路径枚举式 MemorySSA 容易路径爆炸的问题。

做这一步的目的：

如果循环中存在 `mstore`，普通 CFG 路径传播会不断沿 loop back 边产生新的 PathState，导致：

- 循环被反复展开。
- memory 版本不断增加。
- `seen` 去重无法表达循环归纳过程。
- 最后只能依赖最大路径数截断。
- 截断后，后续 `keccak256 / log / call / return` 可能无法追踪到循环构造的 memory 数据。

因此这里将 MemorySSA 从“前向阶段完整枚举循环”改为“前向阶段记录循环摘要，后向读取时按需解析”。

核心做法：

- CFG 构建后识别所有 `YulForLoop`。
- 判断 loop body 内是否存在 memory 修改操作：
  - `mstore`
  - `mstore8`
  - `calldatacopy`
  - `codecopy`
  - `returndatacopy`
  - `mcopy`
- 如果 loop 内没有 memory 写入，则不生成 `LoopMemoryRecord`，同时前向传播不展开 loop body，避免无意义路径爆炸。
- 如果 loop 内有 memory 写入，则建立 `LoopMemoryRecord`，记录：
  - loop header、body、post、exit、backedge 节点。
  - loop condition。
  - induction variable。
  - lower bound、upper bound、step、trip count。
  - loop 内 memory write effect。
- 对 memory 写地址进行分类：
  - `fixed`：每轮写同一个地址，例如 `mstore(ptr, v)`。
  - `affine_range`：按归纳变量写区间，例如 `mstore(add(ptr, mul(i, 0x20)), v)`。
  - `symbolic`：地址可表达但无法确认归纳关系。
  - `unknown`：无法可靠建模。
- 后续只有当语义终点真正读取 memory 时，才调用 lazy resolve。

示例一：固定次数 range 写入。

```Solidity
assembly {
    let ptr := mload(0x40)
    let i := 0
    for { } lt(i, 3) { i := add(i, 1) } {
        mstore(add(ptr, mul(i, 0x20)), i)
    }
    let h := keccak256(ptr, 0x60)
}
```

恢复结果：

```Plain
LoopMemoryRecord L1:
  bound = constant, trip_count = 3
  effect = mem[ptr + i * 32] = i

keccak256 read(ptr, 0x60):
  ptr + 0  = 0
  ptr + 32 = 1
  ptr + 64 = 2
```

示例二：符号次数 range 写入。

```Solidity
assembly {
    let ptr := mload(0x40)
    let i := 0
    for { } lt(i, count) { i := add(i, 1) } {
        mstore(add(ptr, mul(i, 0x20)), calldataload(add(dataOffset, mul(i, 0x20))))
    }
    return(ptr, mul(count, 0x20))
}
```

恢复结果不再直接退化为 unknown，而是生成：

```Plain
MemoryRangeSummary:
  base = ptr
  length = count * 32
  index = i in [0, count)
  stride = 32
  value = calldataload(dataOffset + i * 32)
```

示例三：同一地址循环写入。

```Solidity
assembly {
    mstore(ptr, 0)
    let i := 0
    for { } lt(i, count) { i := add(i, 1) } {
        let old := mload(ptr)
        mstore(ptr, add(old, 1))
    }
    let x := mload(ptr)
}
```

恢复结果：

```Plain
MemoryPhi:
  mem[ptr] = phi(
    preheader: 0,
    backedge: add(old, 1)
  )
```

当前作用：该模块是目前 MemorySSA 中处理循环的核心机制。它不会尝试完整执行循环，只为后续语义恢复提供可追踪的 loop memory summary。

### 5. Storage 恢复模块更新

作用：将 Storage Slot 计算恢复、状态读取恢复、状态写入恢复继续接入新的 CFG / MemorySSA 能力。

做这一步的目的：

前面的 storage 恢复依赖 `keccak256(ptr, len)` 的 memory 输入。如果 memory 输入受分支或循环影响，则旧的线性 MemoryTracker 可能只能得到 unknown。引入 CFG / MemorySSA 后，可以更准确判断某个 slot 计算在当前路径上的真实输入。

核心做法：

- 继续使用 Slither `variable-order` 获取状态变量与 slot 的对应关系。
- 但该文件不要求用户提前提供，pipeline 会在运行时调用 Slither printer 生成。
- `keccak256` 仍然采用按需激活原则：只有被 `sload / sstore` 消费时才作为 storage slot 计算。
- 对于普通 word 级 resolved inputs，继续恢复：
  - mapping slot。
  - nested mapping slot。
  - direct state variable slot。
- 对于 `MemoryRangeSummary`，当前不强行恢复为 mapping，而是保留“hash input is loop-constructed memory range”的信息，避免误判。

示例：

```Solidity
assembly {
    mstore(ptr, user)
    for { } lt(i, 1) { i := add(i, 1) } {
        mstore(add(ptr, 0x20), balances.slot)
    }
    let loc := keccak256(ptr, 0x40)
    let bal := sload(loc)
}
```

Loop-aware MemorySSA 可解析：

```Plain
keccak256 input:
  word0 = user
  word1 = balances.slot
```

后续 storage 恢复可继续得到：

```Solidity
bal = balances[user];
```

### 6. 算术、比较、位运算和环境操作恢复

作用：将 Yul 中常见的算术、比较、位运算和部分 EVM 环境操作恢复为 Solidity 风格表达。

做这一步的目的：

assembly 中大量表达式以函数形式出现，例如 `add(a,b)`、`lt(a,b)`、`iszero(x)`、`shl(96, caller())`。如果不恢复这些表达式，最终 semantic view 会保留大量 Yul 风格函数调用，不利于人工审查，也不利于后续恢复为 Solidity 源码。

当前恢复范围包括：

- `add(a,b)` -> `a + b`
- `sub(a,b)` -> `a - b`
- `mul(a,b)` -> `a * b`
- `div(a,b)` -> `a / b`
- `mod(a,b)` -> `a % b`
- `lt(a,b)` -> `a < b`
- `gt(a,b)` -> `a > b`
- `eq(a,b)` -> `a == b`
- `iszero(x)` -> `!(x)`
- `and(a,b)` -> `a & b`
- `or(a,b)` -> `a | b`
- `xor(a,b)` -> `a ^ b`
- `not(x)` -> `~x`
- `shl(a,b)` -> `b << a`
- `shr(a,b)` -> `b >> a`

同时补充了部分环境操作：

- `caller()` -> `msg.sender`
- `gas()` -> `gasleft()`
- `timestamp()` -> `block.timestamp`

对于 `div / mod`，为了符合 Solidity 高级语言语义，如果除数不是静态非零值，会插入：

```Solidity
require(b != 0);
```

示例：

```Solidity
shl(96, caller())
```

可恢复为：

```Solidity
msg.sender << 96
```

在外部调用参数恢复中，还可以进一步识别为：

```Solidity
abi.encodePacked(bytes20(msg.sender))
```

### 7. 外部调用提取与 Precompile 恢复

作用：提取 assembly 中的 `call / staticcall / delegatecall / callcode`，并将其恢复为 Solidity 低级调用形式；对于固定地址 precompile，尽量恢复为对应高级函数。

做这一步的目的：

Yul 中的外部调用只暴露低级 EVM 参数，例如：

```Solidity
staticcall(gas(), 2, ptr, 20, ptr, 32)
```

它不能直接判断目标合约 ABI，也不能可靠恢复为 `token.transfer(...)` 这类高级合约调用。但它的 call kind、target、gas、value、input memory、output memory、success result 等信息都可以静态提取，至少可以恢复为 Solidity 的低级调用模式。

当前提取字段包括：

- callKind：`call / staticcall / delegatecall / callcode`
- target：原始表达式、可解析地址、是否 precompile
- gas / value
- inputPtr / inputSize
- outputPtr / outputSize
- selector：已知或未知
- arguments：从 MemorySSA 解析出的输入 memory，或保留原始 memory range
- successResult
- returnData

普通外部调用恢复为：

```Solidity
(bool ok, bytes memory returndata) = target.call{gas: gasleft(), value: value}(payload);
```

对于 EVM 固定地址 precompile，则进一步恢复。例如地址 `0x02` 是 SHA2-256 precompile。

原始 Yul：

```Solidity
mstore(ptr, shl(96, caller()))
if iszero(staticcall(gas(), 2, ptr, 20, ptr, 32)) {
    revert(0, 0)
}
let y := mload(ptr)
```

当前可恢复为：

```Solidity
bytes32 sha256_result_13 = sha256(abi.encodePacked(bytes20(msg.sender)));
YvIh = uint256(sha256_result_13);
```

这里不再保留 `yulMemorySlice(...)`，而是从 MemorySSA 中读取 call input memory，识别 `shl(96, msg.sender)` 对应的 `bytes20(msg.sender)` 编码。

当前原则：

- 未知目标合约不强行恢复为 ABI 高级调用。
- 已知 precompile 可以恢复为 Solidity 内置函数或更明确的语义表达。
- 对无法解析的 input/output memory range 保守保留低级调用形式。

### 8. 总 Pipeline 更新

作用：串联 CFG、MemorySSA、分支处理、storage、revert、event、arithmetic、external call 等模块，输出当前 assembly 块的 Solidity-like semantic view。

做这一步的目的：

单独模块只能验证局部能力，最终需要一个总脚本从 Solidity 源码出发，自动完成：

1. 提取 assembly 块。
2. 构建 solc AST 和 Yul CFG。
3. 构建 MemorySSA。
4. 进行分支物化。
5. 生成分支处理后的临时源码。
6. 对临时源码重新生成 solc AST / CFG / Slither 结果。
7. 执行 storage、revert、event、arithmetic、external call 等恢复。
8. 输出每个 assembly 块的处理后视图。

当前 pipeline 的定位仍然是“语义视图”，不是直接替换原始 Solidity 源码。也就是说，它输出的是便于审计和后续恢复的 Solidity-like 中间结果，而不是最终可编译源码。

示例结果片段：

```Solidity
require(_from != address(0));
require(_to != address(0));
XCUz = slot(UbLX[_from]);
qVPd = UbLX[_from];
bytes32 sha256_result_13 = sha256(abi.encodePacked(bytes20(msg.sender)));
YvIh = uint256(sha256_result_13);
unchecked { UbLX[_from] = qVPd - _amount; }
iLho = slot(UbLX[_to]);
bXFg = UbLX[_to];
unchecked { UbLX[_to] = bXFg + _amount; }
emit Transfer(_from, _to, _amount);
```

## 三、当前处理结果

当前新增工作后，处理结果相比 6.18 阶段主要有以下提升：

### 1. CFG 图可视化与控制流检查

现在每个 assembly 块都可以导出 CFG DOT 图，用于检查 Yul AST 到控制流图的转换是否正确。

这解决了之前文本顺序扫描无法准确表达复杂控制流的问题，后续遇到嵌套 `if`、`switch`、`for` 时，可以先检查 CFG，再判断 MemorySSA 或分支处理是否正确。

### 2. 分支影响 memory 时不再直接 unknown

对于下面这种分支影响 slot 计算的代码：

```Solidity
mstore(ptr, a)
if condition {
    mstore(ptr, b)
}
let h := keccak256(ptr, 0x20)
```

现在可以根据 CFG 和 MemorySSA 判断：

```Plain
entry path: mem[ptr] = a
condition path: mem[ptr] = b
```

后续处理时可以将受影响的语义终点分别放在对应路径下，而不是简单输出 unknown。

### 3. 循环写 memory 时不会路径爆炸

测试中固定次数循环可以解析为具体 word：

```Plain
keccak256 read(ptr, 0x60)
  ptr + 0  = 0
  ptr + 32 = 1
  ptr + 64 = 2
```

符号次数循环可以保留摘要：

```Plain
MemoryRangeSummary:
  base = ptr
  length = mul(count, 0x20)
  index = i in [0, count)
  value = calldataload(add(dataOffset, mul(i, 0x20)))
```

同一地址循环写入可以生成：

```Plain
MemoryPhi:
  mem[ptr] = phi(pre_loop_value, loop_update_value)
```

### 4. 外部调用语义更清晰

之前类似下面的调用只能保留为：

```Solidity
require(staticcall(gas(), 2, ptr, 20, ptr, 32));
```

现在如果识别到地址 `0x02`，并且 input memory 可以解析，则可以恢复为：

```Solidity
bytes32 r = sha256(abi.encodePacked(bytes20(msg.sender)));
```

这说明当前模块已经不仅仅是“提取 call 参数”，而是能够对已知 EVM precompile 做语义提升。

## 四、已形成的阶段性原则

1. CFG 图是后续 MemorySSA、分支处理和 backward tracing 的基础。
2. MemorySSA 仍然以单个 assembly 块为作用域，不跨 assembly 块共享状态。
3. 对普通分支采用 path-sensitive MemorySSA，对 loop 采用 summary + lazy resolve，不在前向阶段无限展开循环。
4. 只有 `mload / keccak256 / log / return / revert / call` 等语义终点真正读取 memory 时，才触发 loop lazy materialization。
5. 固定次数 affine loop 可以按需展开；符号次数 affine loop 使用 `MemoryRangeSummary`；同一地址循环写入使用 `MemoryPhi`。
6. 无法可靠判断 alias 或覆盖关系时，局部退化为 `MemoryTop`，不让一个复杂 loop 污染整个 assembly 块。
7. `keccak256` 仍然按需判断是否是 storage slot 计算，只有被 storage 操作消费时才激活为 slot。
8. `revert(0, 0)` 仍遵守最近 condition 优先原则，不做过度合并。
9. Event 恢复仍然必须先匹配 topic0；无法匹配则标注 UnknownEvent。
10. 外部调用中未知目标合约不强行 ABI 恢复；固定地址 precompile 可以恢复为 Solidity 高级函数。
11. 当前 pipeline 输出的是 semantic view，不是最终可编译源码。

## 五、后续还需完成的工作

***这里只是一些设想，实际后面在实现时会动态地按需调整。***

### 1. Memory 消解与最终源码替换

当前结果中仍然会保留部分 `memory[...] = ...` 和 `slot(...)` 中间表示。

后续需要基于 observable semantic endpoints 做 backward slicing，只保留真正参与以下语义的变量和表达式：

- storage read/write
- event emit
- require/revert
- external call
- return
- create/create2
- selfdestruct

对于只用于构造 slot、event data 或 call input 的 memory 写入，在最终 Solidity 源码恢复阶段应移除。

### 2. Error selector 与异常恢复

当前主要处理 `revert(0, 0)`。

后续需要进一步恢复：

- `Error(string)`
- `Panic(uint256)`
- 自定义 error selector
- revert data 中通过 memory 构造的错误参数

这部分可以继续沿用 MemorySSA，从 `revert(ptr, size)` 的 memory range 中解析 selector 和 ABI 参数。

### 3. 更完整的 loop 语义

当前 Loop-aware Lazy MemorySSA 已经可以处理固定次数 affine range、符号次数 affine range 和同一地址 MemoryPhi。

后续仍需优化：

- 多 induction variable。
- 非 32 字节对齐写入。
- `mstore8` 的 byte-level 覆盖。
- copy 指令在 loop 中写入动态区间。
- loop 中嵌套 if 对 memory effect 的控制条件表达。

### 4. 外部调用 ABI 识别

当前未知外部调用只恢复为 Solidity 低级调用形式，这是比较安全的做法。

后续如果要继续提升，可以考虑：

- 根据 selector 匹配常见 ERC20/ERC721 ABI。
- 根据目标地址来源判断是否是状态变量中的 token 地址。
- 根据 input memory 的 ABI 编码恢复参数。
- 根据 return data 使用位置恢复返回值类型。

但这一部分不能过度猜测，否则容易把低级调用误恢复成错误的高级合约调用。

### 5. Opaque Predicate 与噪声识别

当前分支处理已经开始对 unknown memory 分支做保守处理，但还没有系统识别 opaque predicate。

后续需要结合：

- condition 是否恒真/恒假。
- condition 是否控制 storage/event/call/revert。
- 分支内语句是否只影响被丢弃的 unknown memory。
- 分支是否影响最终 observable semantic endpoints。

只有确认不影响关键语义时，才能将其标注为混淆噪声。

### 6. 本地 LLM 辅助高级源码整理

当前确定性分析模块负责恢复事实语义，后续可以考虑让本地 LLM 参与最后一层源码整理，例如：

- 合并临时变量。
- 删除已消解的 memory 操作。
- 将 semantic view 改写为更自然的 Solidity 函数体。
- 根据上下文重命名局部变量。

但本地 LLM 不应作为语义判断来源。所有关键语义仍应来自 CFG、MemorySSA、storage/event/call/revert 等确定性模块。

## 七、总结

当前 Step1 已经从“基础 assembly 语义恢复”推进到“CFG 驱动的数据流恢复”阶段。

6.18 阶段的重点是：先把 Memory、Storage、Revert、Event 等基础模块跑通，让 assembly 块能够输出 Solidity-like semantic view。

本阶段的重点是：解决复杂控制流下的语义正确性问题。为此新增了 solc AST 到 Yul CFG 的构建、path-sensitive MemorySSA、分支物化、Loop-aware Lazy MemorySSA，以及 external call / precompile / arithmetic 等模块更新。

目前的结果已经能够更稳定地处理分支、循环、slot 计算、事件数据、外部调用参数和 precompile 调用。下一阶段重点应放在 memory 消解、异常 selector 恢复、低级调用 ABI 辅助识别，以及最终将 semantic view 整理为更接近可替换 Solidity 源码的形式。
