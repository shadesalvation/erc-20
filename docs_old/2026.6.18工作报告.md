# 2026.6.18 工作报告：Step1 Yul 内联汇编处理

## 一、工作目标

本阶段目标是处理混淆源码中的 Solidity inline assembly，将 assembly 块逐步恢复为更接近 Solidity 高级语义的表示。当前方案不直接修改原始 Solidity 源码，也不动态执行合约，而是先定位并提取每个 assembly 块，再在提取结果上进行语义恢复，最终由总 pipeline 展示每个 assembly 块当前可恢复出的高级语义视图。

当前已完成的恢复范围包括：

- Assembly 所属上下文定位。
- Memory 操作恢复。
- Storage slot 计算恢复。
- 状态读取与状态写入恢复。
- 条件分支中的 `revert(0, 0)` 提取。
- 事件 `log0`-`log4` 提取与 `emit` 恢复。
- 将上述模块串联为从 Solidity 源码输入的一体化 pipeline。

## 二、模块说明

### 1. `assembly_context_report.py`

作用：定位 Solidity 源码中的每个 `assembly { ... }` 块，并提取其所在上下文。

核心输出包括：

- 合约名称。
- 函数名称。
- 函数参数。
- 函数可见性。
- 函数是否为 ERC20 标准入口函数。
- assembly 块源码位置。
- assembly 所在函数是否可由 `transfer`、`transferFrom`、`approve` 等入口触达。

核心思想：

- 使用源码级静态解析，而不是依赖动态执行。
- 先屏蔽注释和字符串，避免误匹配。
- 按合约、函数、assembly 块逐层定位源码范围。
- 对函数调用关系进行静态扫描，得到 ERC20 入口函数到内部函数的可达关系。

当前作用：这是后续所有模块的基础，后续恢复均以该模块定位出的 assembly 块为处理单位。

### 2. `assembly_semantic_ir.py`

作用：将每个 assembly 块解析为基础语义 IR，并完成 memory 操作的初步恢复。

核心思想：

- 每个 assembly 块维护独立的 `MemoryTracker`。
- `MemoryTracker` 类似一个静态虚拟内存区，记录 `mstore`、`calldatacopy`、`codecopy`、`returndatacopy` 等对 memory 的写入。
- 当遇到 `mload`、`keccak256(ptr, size)`、`logN(ptr, size, ...)` 等 memory consumer 时，从当前 `MemoryTracker` 中读取对应 memory 区间。
- 对 Yul 局部变量引入 assembly-local SSA 版本，用于区分同名变量在不同赋值点的含义，降低 backward tracing 误匹配。
- 输出格式保持为类似 SlithIR-SSA 的 txt/语义行形式，而不是 JSON 作为主要展示格式。

当前可恢复内容：

- `mstore` -> `memory[base + offset] = value`。
- `mload` -> `target = memory[ptr]`。
- `keccak256` -> 根据 memory 内容展示 hash 输入。
- `logN` -> 记录 topics 与当时 data 区域的 memory 来源。
- `revert`、`call/staticcall`、条件、循环等基础语句被归类为语义节点。

### 3. `assembly_storage_ir.py`

作用：恢复 Storage Slot 计算、状态读取和状态写入。

核心思想：

- 沿用 `MemoryTracker` 思想，因为 Solidity mapping slot 计算本质上通常依赖 memory 中的 key/base slot 排布。
- 通过 Slither 的 `variable-order` printer 获取状态变量与 slot 的对应关系，但在总 pipeline 中由脚本内部实时调用 Slither 生成，不要求用户提前提供该文件。
- 采用按需激活的方式处理 `keccak256`：普通 `keccak256` 只先作为候选；只有当该 hash 被 `sload`、`sstore` 等 storage 操作实际消费时，才将其判断为 slot 计算。
- 对同名 Yul 变量使用 SSA 版本进行区分，避免后续赋值覆盖前面 slot 语义。

当前可恢复内容：

- `keccak256(key, baseSlot)` -> `slot(mapping[key])`。
- 嵌套 mapping slot -> `slot(mapping[key1][key2])`。
- `sload(slot)` -> `target = stateVarOrMappingAccess`。
- `sstore(slot, value)` -> `stateVarOrMappingAccess = value`。
- 对 `add/sub/mul` 等写入表达式标记 unchecked arithmetic candidate，并以 `unchecked { ... }` 展示。

当前样例中的结果包括：

- `XCUz = slot(UbLX[_from])`。
- `qVPd = UbLX[_from]`。
- `unchecked { UbLX[_from] = qVPd - _amount; }`。
- `iLho = slot(UbLX[_to])`。
- `unchecked { UbLX[_to] = bXFg + _amount; }`。
- `akRJ = slot(wZHA[caller()][_spender])`。
- `wZHA[caller()][_spender] = _amount`。

### 4. `assembly_condition_revert_ir.py`

作用：恢复条件分支中的 `revert(0, 0)` 语义，将其转换为 `require(...)` 形式。

核心思想：

- 当前模块只关注 `revert(0, 0)` 的语义恢复，暂不处理恒真、恒假、不透明谓词等复杂化简。
- 当在某个 condition 下遇到 `revert(0, 0)`，优先将最近一层 condition 转换为 `require(!condition)`。
- 只有当上层 condition 块中没有其他有效操作时，才允许合并上层条件。
- 如果上层 condition 中存在其他有效语句，例如 `let tfe9zci := timestamp()`，则不将上层条件直接合并进同一个 `require`。
- 对地址类型参数的 `iszero(addr)` 做 Solidity 化处理，恢复为 `addr != address(0)`。
- 对 `staticcall` 类型的检查恢复为 `require(staticcall(...))`。

当前样例中的结果包括：

- `if iszero(_from) { revert(0, 0) }` -> `require(_from != address(0));`
- `if iszero(_to) { revert(0, 0) }` -> `require(_to != address(0));`
- `if iszero(staticcall(...)) { revert(0, 0) }` -> `require(staticcall(...));`
- 对包含其他操作的嵌套条件，保持局部恢复，不做过度合并。

### 5. `assembly_event_ir.py`

作用：恢复 Yul `log0`-`log4` 指令对应的事件语义。

核心思想：

- 先解析 Solidity 源码中的 `event` 定义。
- 对非 anonymous event 计算：
  `topic0 = keccak256("EventName(type1,type2,...)")`。
- 遇到 `logN(dataOffset, dataSize, topic0, topic1, ...)` 时，先用 `topic0` 匹配已声明 event。
- 匹配成功后：
  - indexed 参数来自 topics。
  - non-indexed 参数来自 `dataOffset/dataSize` 指向的 memory 区间。
  - data 区域通过当前 assembly 块的 `MemoryTracker` 读取。
- 如果 topic0 无法匹配源码中声明的 event，则不强行恢复为标准事件，而是标注为 `UnknownEvent_<topic0前缀>`。
- 如果 log 之后才写入 data 区域，会在 notes 中标记 `memory_data_written_after_log_at_op_x`，避免用后续 memory 写入倒推历史。

当前样例中的结果包括：

- `_transfer` 中的标准 Transfer 事件：
  `emit Transfer(_from, _to, _amount);`
- `approve` 中的非标准 topic0 log：
  `emit UnknownEvent_8c5be1e5ebec(caller(), _spender, _spender); /* confidence=low */`

其中 `approve` 的 log 未恢复为 `Approval`，原因是其 topic0 与标准 `Approval(address,address,uint256)` topic0 不一致，并且 `_amount` 是在 `log3` 之后才写入 memory。

### 6. `assembly_recovery_pipeline.py`

作用：将前述模块串联为一条从 Solidity 源码输入的总流程。

核心思想：

- 用户只需要提供 Solidity 源码。
- 脚本内部自动调用 Slither printer 生成 `slithir-ssa` 与 `variable-order`。
- 依次执行：上下文定位、基础语义 IR、memory 恢复、storage 恢复、revert 恢复、event 恢复。
- 最终输出每个 assembly 块的原始源码和恢复后的 semantic view。
- 不修改原始源码，不动态执行，不保证输出可直接编译，仅作为逐步恢复源码的中间语义视图。

当前总输出标题为：

`Processed Assembly View After Memory + Storage + Revert + Event Recovery`

## 三、当前处理结果

以当前样例 `TOKENS/0x0068e979c72bbb31373ea8cb47eaefb44978566e/Token.sol` 为例，pipeline 已能展示以下恢复效果。

### 1. `_transfer` assembly 块

已恢复出的主要语义：

```solidity
require(_from != address(0));
require(_to != address(0));
XCUz = slot(UbLX[_from]);
qVPd = UbLX[_from];
Fpzy = sSgI;
require(staticcall(gas(), 2, bbwz, 20, bbwz, 32));
unchecked { UbLX[_from] = qVPd - _amount; }
iLho = slot(UbLX[_to]);
bXFg = UbLX[_to];
unchecked { UbLX[_to] = bXFg + _amount; }
emit Transfer(_from, _to, _amount);
```

### 2. `approve` assembly 块

已恢复出的主要语义：

```solidity
ZFHJ = slot(wZHA[caller()]);
akRJ = slot(wZHA[caller()][_spender]);
wZHA[caller()][_spender] = _amount;
emit UnknownEvent_8c5be1e5ebec(caller(), _spender, _spender); /* confidence=low */
```

这里标注为 `UnknownEvent` 是因为 topic0 不匹配源码声明的 `Approval` 事件。当前 log 的 data 区域在 log 发生时保存的是 `_spender`，而不是 `_amount`。

### 3. `_spendAllowance` assembly 块

已恢复出的主要语义包括：

- 嵌套 mapping slot 的多阶段恢复。
- 部分 `sload` 恢复为 `wZHA[...]` 访问。
- 条件下的 `revert(0, 0)` 恢复为 `require(...)`。
- 条件内重新计算 slot 时，SSA 能区分同名 Yul 变量的不同版本。

当前仍存在部分表达式只恢复到中间状态，例如某些 inline `sload(Jfwv)` 尚未完全替换为最终 mapping access。这属于后续表达式替换与控制流语义整理阶段需要继续处理的问题。

## 四、已形成的阶段性原则

1. 每个 assembly 块独立维护 MemoryTracker，不跨块共享 memory 状态。
2. MemoryTracker 只记录静态语义，不执行合约。
3. `keccak256` 不再一律识别为 slot，只有被 storage 操作消费时才激活为 slot 计算。
4. 对 Yul 局部变量引入 SSA，降低同名变量复用导致的错误回溯。
5. `revert(0, 0)` 的恢复遵守最近 condition 优先原则，不做过度合并。
6. Event 恢复必须先匹配 topic0；无法匹配时标注 UnknownEvent，而不是误恢复为标准事件。
7. log 的 data 参数必须按 log 发生时的 memory 状态读取，不能用后续 `mstore` 补写历史。

## 五、后续还需完成的工作

### 1. 控制流结构恢复

当前 processed view 仍是偏线性的语义视图，后续需要进一步恢复 Solidity 风格的 `if`、嵌套块、条件作用域和缩进结构，使输出更接近可读源码。

### 2. 表达式替换与变量传播

需要继续处理：

- inline `sload(...)` 的更完整替换。
- SSA 名称到展示名称的统一清理。
- 中间变量传播。
- `add/sub/mul/eq/lt/iszero` 等 Yul 表达式进一步 Solidity 化。

### 3. Storage 恢复增强

需要继续处理：

- 更复杂的动态 offset。
- packed storage。
- array、struct、bytes/string 等非简单 mapping slot。
- 条件分支下 memory 写入对 slot 计算的多候选表达。

### 4. Event 恢复增强

需要继续处理：

- anonymous event。
- dynamic indexed 参数。
- dynamic non-indexed 参数的 ABI data 解码。
- 多事件候选时的置信度排序。
- UnknownEvent 的参数命名与展示格式优化。

### 5. 最终源码替换阶段

当前 pipeline 只输出 semantic view，尚未替换原 Solidity 源码中的 assembly 块。后续需要在 IR 更稳定后，将恢复出的 Solidity 风格语句整体替换回原 assembly 块位置，并形成可人工审阅的恢复源码。

### 6. 测试体系补充

需要继续构造覆盖以下场景的测试：

- 多层 mapping。
- mapping + condition + reuse variable。
- log 的标准事件、非标准 topic、anonymous event。
- `calldatacopy/codecopy/returndatacopy` 参与 hash 或 event data。
- 循环写 memory 与动态 offset。
- revert 条件中混入其他有效操作。

## 七、总结

当前 Step1 已经从“定位 assembly 块”推进到“多模块语义恢复 + 总 pipeline 展示”的阶段。Memory、Storage、Revert、Event 四类关键语义都已经形成了独立模块，并能在当前 ERC20 样例中恢复出大量 Solidity 风格表达。

下一阶段重点不应是继续简单堆规则，而是围绕控制流、表达式传播、复杂 storage 类型和最终源码替换四个方向，把当前 semantic view 进一步整理为更稳定、更接近 Solidity 源码的恢复结果。
