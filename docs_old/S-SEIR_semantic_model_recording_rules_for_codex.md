# S-SEIR Semantic Model Recording Rules for Codex

## 0. Purpose

This document defines how to record Solidity source code and Yul / inline assembly code into a unified semantic IR called **S-SEIR**.

S-SEIR is used before any LLM-based code rendering. Its purpose is to provide a deterministic, static-analysis-friendly representation for:

1. Solidity-like source reconstruction;
2. security-behavior slicing;
3. logical vulnerability detection;
4. later rendering or reporting.

Do **not** implement LLM calls in this stage.

---

## 1. Core Model

A function-level S-SEIR object has this structure:

```json
{
  "function": "function_name",
  "source_statements": [],
  "control": {},
  "expr_roles": [],
  "effects": [],
  "semantic_overlays": [],
  "projection_policies": [],
  "security_facts": []
}
```

### 1.1 Meaning of each part

| Field | Meaning |
|---|---|
| `source_statements` | Original Solidity / Yul / SlithIR statements. Other nodes refer to them through `stmt_refs`. |
| `control` | Unified control structure: blocks, CFG edges, branch/revert/return terminators. |
| `expr_roles` | Expressions annotated by semantic role, such as `mapping_slot_expr`, `revert_payload_ptr`, `call_target`. |
| `effects` | Low-level side effects: memory read/write, storage read/write, call, log, revert, return. |
| `semantic_overlays` | Higher-level semantic interpretation of effects, such as `MappingWrite`, `RawRevertBytes`, `EventEmit`. |
| `projection_policies` | Whether an overlay can be exactly projected to high-level Solidity. |
| `security_facts` | Facts used for vulnerability or security-behavior analysis. |

## 2. Global Design Rules

### Rule G1: Do not store confidence

Do not add `confidence` to any formal S-SEIR node.

Bad:

```json
{
  "kind": "MappingWrite",
  "confidence": 0.91
}
```

Good:

```json
{
  "kind": "MappingWrite",
  "stmt_refs": ["asm_s4", "asm_s5"]
}
```

Uncertainty should be represented by `projection_policies`, `reason`, or `unresolved` nodes, not by probability.

---

### Rule G2: Keep evidence lightweight

Do not build a complex provenance graph. Each node only stores source statement references:

```json
{
  "stmt_refs": ["sol_s1", "asm_s2"]
}
```

The actual source text is stored once in `source_statements`.

---

### Rule G3: Separate effects from overlays

Effects are low-level semantic facts. Overlays are high-level interpretations.

Example:

```yul
sstore(slot, value)
```

Effect:

```json
{
  "kind": "StorageWrite",
  "attrs": {
    "slot": "slot",
    "value": "value"
  }
}
```

Overlay, only if the slot can be interpreted:

```json
{
  "kind": "MappingWrite",
  "attrs": {
    "state_var": "balances",
    "key": "from",
    "value": "value"
  }
}
```

---

### Rule G4: Expression roles describe purpose, not only syntax

Expression roles should record why an expression matters.

Example:

```yul
revert(add(32, returndata), returndata_size)
```

`add(32, returndata)` is syntactically addition, but semantically it is a revert payload pointer:

```json
{
  "text": "add(32, returndata)",
  "normalized": "returndata.data",
  "role": "revert_payload_ptr"
}
```

---

### Rule G5: Projection policy is static-analysis output

`ProjectionPolicy` is not an LLM decision. It is generated by static rules after semantic overlays are built.

Example:

```json
{
  "exact_solidity_equivalent": false,
  "output_kind": "assembly_preserved",
  "reason": "raw_revert_payload"
}
```

## 3. Data Schemas

### 3.1 SourceStatement

```python
class SourceStatement:
    stmt_id: str
    lang: str          # solidity | yul | slithir
    text: str
    src: str | None
    function: str
    block: str | None
```

Example:

```json
{
  "stmt_id": "asm_s2",
  "lang": "yul",
  "text": "revert(add(32, returndata), returndata_size)",
  "src": "1234:48:0",
  "function": "_revert",
  "block": "bb_revert_bubble"
}
```

---

### 3.2 ControlBlock

```python
class ControlBlock:
    block_id: str
    stmts: list[str]
    terminator: dict | None
```

Supported terminators:

```text
Branch
Jump
Return
Revert
Stop
Fallthrough
```

Example:

```json
{
  "block_id": "bb_entry",
  "stmts": ["sol_s1"],
  "terminator": {
    "kind": "Branch",
    "condition": "returndata.length > 0",
    "true_block": "bb_revert_bubble",
    "false_block": "bb_failed_inner_call"
  }
}
```

---

```python
class ExpressionRole:
```

## 4. Solidity Source Recording Rules

### Rule S1: Solidity `require`

Source:

```solidity
require(_from != address(0));
```

Record source statement:

```json
{
  "stmt_id": "sol_s1",
  "lang": "solidity",
  "text": "require(_from != address(0));",
  "function": "_transfer",
  "block": "bb_1"
}
```

Expression role:

```json
{
  "expr_id": "expr_1",
  "text": "_from != address(0)",
  "role": "guard_condition",
  "normalized": "_from != address(0)",
  "type_hint": "bool",
  "stmt_ref": "sol_s1"
}
```

Effect:

```json
{
  "effect_id": "eff_1",
  "kind": "Require",
  "attrs": {
    "condition": "_from != address(0)",
    "revert_payload": "empty_or_default"
  },
  "stmt_refs": ["sol_s1"]
}
```

Overlay:

```json
{
  "overlay_id": "ov_1",
  "kind": "RequireOverlay",
  "attrs": {
    "condition": "_from != address(0)"
  },
  "effects": ["eff_1"],
  "stmt_refs": ["sol_s1"]
}
```

Projection policy:

```json
{
  "policy_id": "pol_1",
  "target_overlay": "ov_1",
  "exact_solidity_equivalent": true,
  "output_kind": "solidity_statement",
  "reason": "solidity_require",
  "stmt_refs": ["sol_s1"]
}
```

Source:

```yul

```

```json

  "expr_id": "expr_y1",
  "text": "mload(0x40)",

  "normalized": "free_mem_ptr",
```

```json

  "effect_id": "eff_y1",
```

```json
{
  "policy_id": "pol_y1",
```

## 6. Projection Policy Rules

### Rule P1: Exact Solidity equivalent

Set:

```json
{
  "exact_solidity_equivalent": true
}
```

when the overlay can be represented by a high-level Solidity construct without changing semantics.

Examples:

| Overlay | output_kind | reason |
|---|---|---|
| `RequireOverlay` | `solidity_statement` | `empty_revert_guard` |
| `CustomErrorRevert` | `solidity_statement` | `custom_error_revert` |
| `MappingRead` | `solidity_expression` | `mapping_slot_read` |
| `MappingWrite` | `solidity_statement` | `mapping_slot_write` |
| `EventEmit` with known event | `solidity_statement` | `known_event_log` |

---

### Rule P2: Preserve assembly

Set:

```json
{
  "exact_solidity_equivalent": false,
  "output_kind": "assembly_preserved"
}
```

when high-level Solidity cannot exactly express the low-level behavior.

Examples:

| Overlay | reason |
|---|---|
| `RawRevertBytes` | `raw_revert_payload` |
| unknown arbitrary `return(ptr, size)` | `unknown_return_payload` |
| memory manipulation with no high-level equivalent | `unstructured_memory_effect` |

---

### Rule P3: Low-level call statement

For low-level calls, use:

```json
{
  "output_kind": "low_level_call_statement"
}
```

If ABI is known, `exact_solidity_equivalent` may be `true` only for a semantically equivalent low-level Solidity call form, such as:

```solidity
(bool ok, ) = target.call(data);
```

If ABI is unknown, keep:

```json
{
  "exact_solidity_equivalent": false,
  "reason": "unknown_call_abi"
}
```

---

### Rule P4: Unresolved

Use:

```json
{
  "output_kind": "unresolved",
  "reason": "..."
}
```

when the system cannot interpret the overlay or effect.

Do not guess.

---

## 7. Security Fact Rules

Security facts are derived from semantic overlays and effects. They are used for vulnerability analysis and security-behavior slicing.

### Rule SF1: Balance update

From:

```json
{
  "kind": "MappingWrite",
  "attrs": {
    "state_var": "balances",
    "key": "from",
    "value": "old - amount"
  }
}
```

Generate:

```json
{
  "kind": "BalanceUpdate",
  "attrs": {
    "state_var": "balances",
    "account": "from",
    "delta": "-amount"
  }
}
```

---

### Rule SF2: Allowance update

From mapping write to nested mapping:

```solidity
allowances[owner][spender] = value;
```

Generate:

```json
{
  "kind": "AllowanceUpdate",
  "attrs": {
    "owner": "owner",
    "spender": "spender",
    "value": "value"
  }
}
```

---

### Rule SF3: External call

From `Call`, `DelegateCall`, or `StaticCall` effect:

```json
{
  "kind": "ExternalCall",
  "attrs": {
    "target": "target",
    "value": "value",
    "call_type": "call"
  }
}
```

Generate security fact:

```json
{
  "kind": "ExternalCall",
  "attrs": {
    "target": "target",
    "value": "value",
    "call_type": "call"
  }
}
```

---

### Rule SF4: Reentrancy-relevant order

If an external call occurs before a related storage update in the same control path, generate:

```json
{
  "kind": "ExternalCallBeforeStateUpdate",
  "attrs": {
    "call": "eff_call",
    "state_update": "eff_sstore"
  }
}
```

This does not by itself prove reentrancy. It is a candidate fact.

---

### Rule SF5: Event-state consistency

If a `TransferEvent` and balance updates appear in the same function path, link them:

```json
{
  "kind": "EventStateLink",
  "attrs": {
    "event": "Transfer",
    "state_updates": ["sf_balance_from", "sf_balance_to"]
  }
}
```

If event amount differs from state delta and no fee/tax model is detected, generate:

```json
{
  "kind": "EventStateMismatchCandidate",
  "attrs": {
    "event_amount": "event_amount",
    "state_delta": "state_delta"
  }
}
```

---

### Rule SF6: Hidden transfer policy / blacklist candidate

If transfer success depends on an external call, hidden mapping, blacklist-like mapping, or unknown policy state, generate:

```json
{
  "kind": "TransferPolicyDependency",
  "attrs": {
    "condition": "cond",
    "dependency": "external_call_or_storage_flag"
  }
}
```

## 9. Implementation Passes

Implement or adapt the project into these passes.

### Pass 0: Source Statement Collector

Input:

```text
Solidity AST
Slither nodes
Yul AST / assembly parser output
```

Output:

```text
source_statements
```

Tasks:

1. assign `stmt_id`;
2. store `lang`, `text`, `src`, `function`, `block`;
3. ensure all later nodes use `stmt_refs` only.

---

### Pass 1: Control Builder

Input:

```text
Slither CFG
assembly / Yul CFG
SourceStatementTable
```

Output:

```text
control
```

Tasks:

1. unify Solidity and Yul blocks;
2. identify branch, return, revert, fallthrough;
3. embed assembly block into Solidity function context.

---

### Pass 2: Expression Role Analyzer

Input:

```text
Yul expression tree
Solidity type information
MemorySSA
Storage layout
Def-use information
SourceStatementTable
```

Output:

```text
expr_roles
```

Must implement first:

```text
mload(0x40) -> free_memory_pointer
mload(bytes_obj) -> bytes_length_ptr / revert_payload_size
add(bytes_obj, 32) -> bytes_data_ptr / revert_payload_ptr
keccak256(p, 64) after mstore(key, slot) -> mapping_slot_expr
call arguments -> call_* roles
branch conditions -> guard_condition / branch_condition
```

---

### Pass 3: Effect Lifter

Input:

```text
MemorySSA
StorageSSA
Call analysis
Event analysis
Revert analysis
Expression roles
```

Output:

```text
effects
```

Tasks:

1. mload/mstore -> MemoryRead/MemoryWrite;
2. sload/sstore -> StorageRead/StorageWrite;
3. call/delegatecall/staticcall -> Call/DelegateCall/StaticCall;
4. log0-log4 -> EventLog;
5. revert/return -> Revert/Return.

---

### Pass 4: Semantic Overlay Builder

Input:

```text
effects
expr_roles
def-use
storage layout
event signatures
call ABI info if available
```

Output:

```text
semantic_overlays
```

Must implement first:

```text
RawRevertBytes
CustomErrorRevert
RequireOverlay
MappingSlot
MappingRead
MappingWrite
```

Optional next:

```text
EventEmit
ExternalCall
LowLevelCall
```

---

### Pass 5: Projection Policy Classifier

Input:

```text
semantic_overlays
expr_roles
Solidity language capability rules
known type / ABI information
```

Output:

```text
projection_policies
```

Tasks:

1. decide exact Solidity equivalence;
2. assign output_kind;
3. assign reason;
4. never call an LLM.

---

### Pass 6: Security Fact Builder

Input:

```text
semantic_overlays
effects
control graph
projection policies
```

Output:

```text
security_facts
```

Tasks:

1. derive balance/allowance updates;
2. derive guard conditions;
3. derive external calls;
4. derive event-state links;
5. derive candidate logical vulnerability facts.

## 12. Completion Criteria

The implementation is acceptable when:

1. S-SEIR JSON can be built per function;
2. all major nodes use `stmt_refs`;
3. no formal node contains `confidence`;
4. RawRevertBytes is detected correctly;
5. mapping slot construction is represented as ExpressionRole + MappingSlot overlay;
6. external calls are represented as Call effect and optional ExternalCall overlay;
7. projection policies are generated statically;
8. security facts are generated from overlays and effects;
9. existing tests continue to pass.
